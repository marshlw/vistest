## 1. Требования

| Что | Версия | Обязательно |
|---|---|---|
| Python | 3.10+ | да |
| Playwright + браузеры | ставится автоматически | для тестов страниц |
| Docker | любой свежий | для эталонного рендера и CI |
| Git | — | для истории эталонов и определения ветки |

Ядро сравнения живёт на трёх пакетах (`numpy`, `opencv-python-headless`, `pillow`).
Всё остальное — опционально: браузер, сервис, ONNX, LLM ставятся отдельными
экстрами.

## 2. Установка

### Windows

```powershell
cd D:\project\visual-testing
.\run.ps1 setup
```

Если PowerShell ругается на политику выполнения:

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1 setup
```

### Linux / macOS

```bash
cd ~/project/visual-testing
chmod +x run.sh
./run.sh setup
```

### Что делает `setup`

1. Создаёт `.venv` в корне проекта (`.venv\Scripts` на Windows, `.venv/bin` на остальных).
2. Ставит `vistest` в editable-режиме со всеми экстрами.
3. Ставит Chromium для Playwright (на Linux ещё и системные библиотеки).

Проверить, что всё встало:

```bash
python run.py doctor
```

Вывод покажет ОС, интерпретатор, наличие каждой зависимости, docker/git и
сколько эталонов уже создано.

`doctor` отвечает на два разных вопроса, и различать их важно:

| Команда | Вопрос |
|---|---|
| `python run.py doctor` | что не так с **машиной** |
| `python run.py doctor URL` | что не так с **проектом** — сколько у него собственного шума |

Второй вариант разобран в разделе «Сколько шума в вашем проекте».

### Ручная установка (если не хочется лаунчера)

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux/macOS
pip install -e ".[full]"
playwright install chromium
```

### Шаг 2. Прогнать реальные тесты на демо-странице

```bash
python run.py test examples/ -v
```

Первый прогон создаёт эталоны и помечает тесты как `NEW_BASELINE` — это
нормально. Запустите ещё раз:

```bash
python run.py test examples/ -v
```

Второй прогон уже сравнивает. Всё должно пройти зелёным, несмотря на то что
на демо-странице тикает счётчик и крутится спиннер — их поймала stability-маска.

### Шаг 3. Открыть UI

```bash
python run.py ui
```

Откроется `http://127.0.0.1:8420/ui/`. Пока прогоны не отправлялись в сервис,
список будет пустым — см. [раздел 9](#9-сервис-ui-и-метрики).

### Шаг 4. Убедиться, что регресс ловится

Откройте `examples/demo_page.html` и поменяйте цвет кнопки:

```css
.cta{background:#e74c3c;   /* было var(--accent) */
```

Прогоните тесты — они упадут, а в `.vistest/runs/<run_id>/landing_png/`
появятся `boxes.png`, `heatmap.png`, `blink.gif` и остальное.

## 3.1. Быстрое создание эталонов мышью

Главный барьер визуального тестирования — не движок, а рутина заведения
снимков. Написать тридцать `assert_screenshot`, подобрать селекторы и маски —
работа на день. Режим записи превращает это в десять минут кликов.

### Запуск

```bash
python run.py record https://my-app.local
python run.py record https://my-app.local --viewport 390x844
python run.py record --cdp http://localhost:9222      # к уже открытому Chrome
```

**То же самое кнопкой.** Вкладка «Эталоны» в интерфейсе, панель «● Записать
эталоны мышью»: поле для адреса, размер окна, имя проекта и галочка page
objects. Это главный вход для QA без Python, и держать его только в командной
строке значило отдавать его ровно тем, кому он меньше всего нужен.

Одна особенность, о которой интерфейс предупреждает прямо: **браузер откроется
на машине, где запущен сервис**, а не у того, кто нажал кнопку. Для обычного
сценария (сервис у инженера на своей машине) это ровно то, что нужно; для
инсталляции, доступной команде по сети, — бессмысленно, и потому запись оттуда
по умолчанию запрещена (`VISTEST_RECORD_UI`: `local` — по умолчанию, `all` —
разрешить, `off` — выключить).

Запись идёт, пока вы не нажмёте «Готово» в панели браузера — именно тогда
собираются тесты. Кнопка «■ Остановить» в интерфейсе нужна для случая, когда
браузер закрыли, а процесс остался: тесты в этом случае не соберутся.

Откроется браузер с панелью в правом нижнем углу.

### Что делает панель

| Кнопка | Что происходит |
|---|---|
| **Снять страницу** | эталон всей страницы. Горячая клавиша `Ctrl+Shift+S` |
| **Выбрать элемент** | наведите мышью — элемент подсвечивается, клик снимает только его. Селектор вычисляется автоматически, приоритет у `data-testid` |
| **Игнор-зона** | выделите мышью прямоугольник — эта область не будет сравниваться. Записывается в эталон навсегда |
| **Сбросить зоны** | очистить накопленные зоны |
| **Готово** | сохранить всё и выйти |

Имя снимка можно не вводить — подставится из адреса страницы. Панель
перетаскивается за заголовок, сворачивается и **никогда не попадает в
эталон**: перед каждым снимком она прячется.

### Порядок работы

1. Запустите `record` с адресом тестового стенда.
2. Залогиньтесь, дойдите до нужного состояния — это обычный браузер, всё
   работает как всегда.
3. Жмите «Снять страницу» или снимайте отдельные компоненты.
4. Навигация между страницами не мешает: панель переживает переходы.
5. «Готово».

### Что получается на выходе

```
Сохранено эталонов: 7
  .vistest/baselines/win-chromium-1x

Сгенерирован тест: tests/test_visual_recorded.py
Проверьте его прогоном:  python run.py test tests/test_visual_recorded.py
```

Сгенерированный файл — обычный pytest + Playwright, который можно и нужно
править руками:

```python
"""Визуальные тесты, записанные через `vistest record` 2026-08-07 14:22.
...
"""

import pytest

BASE_URL = "https://my-app.local"


@pytest.mark.visual
def test_checkout(page, visual):
    """3 снимка /checkout при 1440×900"""
    page.goto(BASE_URL + "/checkout")
    visual.assert_screenshot("checkout.png")
    visual.assert_screenshot("order-summary.png", clip_selector="#order-summary")
    visual.assert_screenshot("payment-form.png", clip_selector="form.payment")


def test_checkout_mobile(page, visual):
    """страница /checkout при 390×844"""
    page.set_viewport_size({"width": 390, "height": 844})
    page.goto(BASE_URL + "/checkout")
    visual.assert_screenshot("checkout-mobile.png")
```

Снимки группируются по странице и размеру окна; общий домен выносится в
`BASE_URL`. Если файл уже существует, прежняя версия сохраняется как `.bak`.

Флаг `--no-code` создаст только эталоны, без генерации теста.

### Page objects: `--pom`

```bash
python run.py record https://shop.example --pom
python run.py codegen --pom            # пересобрать из паспортов эталонов
```

Плоский сгенерированный тест с селекторами внутри читается ровно один раз — в
момент генерации. Через месяц вёрстку меняют, двадцать тестов краснеют, и
править приходится в двадцати местах. Именно на этом умирают записанные тесты
во всех рекордерах: их проще перезаписать, чем починить, а перезапись теряет
всё, что человек дописал руками.

С `--pom` рядом появляется `tests/pages/` — по классу на страницу:

```python
# tests/pages/checkout_page.py
class CheckoutPage:
    """/checkout"""

    PATH = "/checkout"

    def __init__(self, page):
        self.page = page

    # --- локаторы: сгенерировано, ваши правки сохраняются ---

    @property
    def submit_button(self):
        """Оформить заказ"""
        return self.page.get_by_test_id("checkout-submit")

    @property
    def login_field(self):
        """textbox: Логин"""
        return self.page.get_by_role("textbox", name="Логин")

    # --- конец локаторов ---

    def open(self, base_url=""):
        self.page.goto(base_url + self.PATH)
        return self

    def login(self):
        self.login_field.fill(os.environ["VISTEST_USER"])
        self.password_field.fill(os.environ["VISTEST_PASSWORD"])
        self.submit_button.click()
        return self
```

```python
# tests/test_visual_shop.py
def test_checkout(page, visual):
    checkout = CheckoutPage(page)
    checkout.open(BASE_URL)
    checkout.login()
    visual.assert_screenshot("checkout.png")
```

**Локаторы выбираются по прочности, а не по удобству генератора:**

| Приоритет | Локатор | Что переживает |
|---|---|---|
| 1 | `get_by_test_id("checkout-submit")` | перевёрстку и перевод интерфейса |
| 2 | `get_by_role("button", name="Оформить")` | перевёрстку; ломается при переводе |
| 3 | `locator("main > div:nth-of-type(3)")` | ничего |

Роль берётся только если пара «роль + доступное имя» на странице уникальна:
иначе Playwright в strict mode упадёт на неоднозначном локаторе. CSS-путь идёт
последним и с комментарием, как его укрепить — проставьте элементу
`data-testid`, и следующая пересборка заменит локатор автоматически.

**Пересборка не затирает ваши правки.** Блок локаторов размечен маркерами:
генератор дописывает в него новые свойства и не трогает изменённые. Всё за
пределами блока не трогается вообще. Убрали маркеры — файл перестаёт
обновляться совсем, то есть вы взяли его под свой контроль.

Никакого трёхстороннего слияния здесь нет намеренно: непредсказуемый
генератор кода хуже отсутствующего.

Каталог тестов при этом становится пакетом (`__init__.py`) — иначе
`from .pages.checkout_page import CheckoutPage` не сработает.

## 3.2. Подключение к уже написанным тестам

Переписывать существующий пакет тестов ради визуальных проверок никто не станет.
Поэтому VisTest подключается точечно: тесты остаются на своём фреймворке и языке,
а сравнение выполняет движок VisTest.

### Python: Selenium, unittest, свои обёртки

Драйвер определяется автоматически — Playwright `Page` и Selenium `WebDriver`
работают одинаково. Для Selenium full-page снимается через CDP (Chrome/Edge), а
в остальных браузерах сшивается прокруткой.

```python
from vistest.integrations import visual_check

def test_checkout(browser):            # ваш существующий тест на Selenium
    browser.get("https://shop/checkout")
    visual_check(browser, "checkout.png")
```

Одна строка. Результаты всех вызовов за процесс собираются в один прогон,
`run.json` пишется автоматически при выходе.

Для unittest есть миксин:

```python
import unittest
from vistest.integrations import VisualTestCase

class CheckoutTest(VisualTestCase, unittest.TestCase):
    def setUp(self):
        self.driver = webdriver.Chrome()

    def test_page(self):
        self.driver.get(URL)
        self.assert_screenshot("checkout.png")
        self.assert_screenshot("summary.png", clip_selector="#order-summary")
```

Явная сессия, если нужен свой `run_id` или отдельная сводка:

```python
from vistest.integrations import visual_session

with visual_session(run_id="build-4821") as vs:
    vs.check(driver, "step1.png")
    vs.check(driver, "step2.png", soft=True)      # не бросать, только вернуть
```

Если скриншот делает чужой код и у вас на руках только байты или файл:

```python
vs.check_image("checkout.png", png_bytes)
vs.check_image("checkout.png", "screenshots/checkout.png")
```

### Другие языки: HTTP

Поднимите сервис (`python run.py ui`) и отправляйте снимки в `POST /api/check`:

```bash
curl -sf -X POST http://localhost:8420/api/check \
  -F name=checkout.png \
  -F image=@shot1.png \
  -F frames=@shot2.png -F frames=@shot3.png \
  -F 'options={"fail_severity": 30}'
```

Ответ — вердикт, метрики, список изменившихся регионов с селекторами и ссылки
на артефакты. Полный контракт, готовые клиенты и примеры для Playwright JS,
Cypress, Java и C# — в [`clients/README.md`](../clients/README.md).

Для Node есть клиент без зависимостей:

```js
import { VisTest } from './clients/vistest.mjs';
const vt = new VisTest({ apiUrl: 'http://localhost:8420' });

test.beforeEach(async ({ context }) => { await vt.installOnContext(context); });

test('checkout', async ({ page }) => {
  await page.goto('/checkout');
  await vt.checkPage(page, 'checkout.png');
});
```

### Без сервиса: CLI

Если проще вызвать процесс, чем ходить по HTTP:

```bash
vistest check checkout.png shot.png --frames shot2.png shot3.png
vistest check checkout.png shot.png --set fail_severity=40 --json
vistest check checkout.png shot.png --api http://localhost:8420
```

Код возврата `0` — прошло, `1` — регресс. Работает и локально, и через сервис;
результат одинаковый.

### Одинаковая стабилизация для всех клиентов

`GET /api/stabilize.js` отдаёт тот же скрипт, что использует Python-раннер:
заморозка анимаций, детерминированные `Math.random` и `Date`, ожидание шрифтов
и lazy-load, снятие DOM-снепшота. Инжектируйте его в страницу — и снимки из
JS-тестов станут сопоставимы с питоновскими.

```js
window.__vistest.freeze()          // заморозить анимации, курсор, скроллбары
await window.__vistest.settle()    // прокрутить, дождаться шрифтов и картинок
window.__vistest.dom()             // DOM-снепшот для привязки к селекторам
```

### Что стоит передавать

**Несколько кадров.** Пришлите 2–3 снимка подряд (`frames`) — различия между
ними по определению не регресс, VisTest замаскирует динамику автоматически. С
одним кадром авто-детект выключен, и придётся описывать маски руками.

**DOM-снепшот.** Даёт привязку регионов к элементам: в отчёте будет
`REMOVED button[data-testid="checkout-submit"] "Оформить заказ"` вместо
координат прямоугольника.

**`run_key`.** Объединяет проверки в один прогон в UI. Удобно передавать туда
id сборки CI.

## 3.3. Страницы за авторизацией

Без этого визуальное тестирование покрывает только публичные страницы — то есть
почти ничего в реальном продукте. Личный кабинет, корзина, админка, любая форма
после логина недоступны.

Решение — **шаги**: действия, которые выполняются после перехода по адресу и до
захвата снимка.

### Секреты

Пароли в конфиге не хранятся. Пишете имя переменной, значение подставляется при
запуске:

```
.vistest/secrets.env          ← файл в .gitignore, подхватывается автоматически

VISTEST_USER=qa@example.com
VISTEST_PASSWORD=hunter2
BASE_URL=https://stage.my-app.local
```

В CI просто задайте те же переменные окружения. Если переменная не найдена,
VisTest падает с понятной ошибкой, а не вводит пустой пароль и не оставляет вас
разбираться с непонятным диффом.

### Логин описывается один раз

В `vistest.yaml`:

```yaml
flows:
  login:
    - {action: goto,     url: "${BASE_URL}/login"}
    - {action: fill,     selector: "#username", value: "${VISTEST_USER}"}
    - {action: fill,     selector: "#password", value: "${VISTEST_PASSWORD}"}
    - {action: click,    selector: "button[type=submit]"}
    - {action: wait_for, selector: "[data-testid=user-menu]"}

auth:
  flow: login
  reuse_state: true       # логиниться один раз на прогон, а не на каждый снимок
  state_ttl_minutes: 60
```

Дальше любой снимок подключает его одним шагом:

```yaml
- {action: flow, name: login}
```

`reuse_state` принципиально важен: прогон из пятидесяти снимков за логином
означал бы пятьдесят авторизаций — это минуты времени и верный способ поймать
rate-limit. VisTest логинится один раз, сохраняет куки и localStorage в
`.vistest/state/login.json` и переиспользует их.

### Три способа задать шаги

**1. Мышью при записи.** В панели `record` есть кнопка «● Писать действия».
Включите её, пройдите логин и путь до нужного экрана как обычно — клики, ввод и
переходы записываются сами. Поле пароля распознаётся и сохраняется как
`${VISTEST_PASSWORD}`, само значение никуда не попадает. Запись переживает
переходы между страницами, так что редирект после входа не мешает.

**2. В UI.** Кнопка «Шаги» на карточке эталона: редактор с готовыми пресетами
(«Авторизация», «Форма входа», «Закрыть баннер cookies», «Открыть модалку») и
кнопкой «Сохранить и проверить».

**3. В YAML для `vistest snap`:**

```yaml
snapshots:
  - url: "${BASE_URL}/account"
    name: "account.png"
    steps:
      - {action: flow, name: login}

  - url: "${BASE_URL}/checkout"
    name: "checkout-payment.png"
    steps:
      - {action: flow, name: login}
      - {action: click,    selector: "[data-testid=pay-tab]"}
      - {action: wait_for, selector: ".payment-form"}
```

### Доступные действия

| Действие | Параметры | Что делает |
|---|---|---|
| `goto` | `url` | перейти по адресу |
| `click` | `selector` | кликнуть |
| `fill` | `selector`, `value` | очистить и ввести текст |
| `type` | `selector`, `value`, `delay` | набрать посимвольно |
| `press` | `selector`, `value` | нажать клавишу |
| `select` | `selector`, `value` | выбрать в `<select>` |
| `check` / `uncheck` | `selector` | чекбокс |
| `hover` | `selector` | навести курсор |
| `scroll` | `selector` или `value` | прокрутить к элементу или на N пикселей |
| `wait` | `ms` | пауза |
| `wait_for` | `selector`, `state` | дождаться элемента |
| `wait_for_url` | `url` | дождаться адреса (можно с `*`) |
| `eval` | `value` | выполнить JS |
| `flow` | `name` | вызвать сценарий из `vistest.yaml` |

Список намеренно короткий: это способ довести страницу до нужного состояния, а
не замена функциональным тестам.

Есть и краткая строчная форма для быстрого набора руками:

```yaml
steps:
  - "goto ${BASE_URL}/login"
  - "fill #username ${VISTEST_USER}"
  - "click button[type=submit]"
  - "wait_for .user-menu"
```

### В сгенерированном коде

Записанные шаги превращаются в обычные вызовы Playwright — читаемо и правится
без документации:

```python
@pytest.mark.visual
def test_auth_account(page, visual):
    """страница /account при 1440×900, после 5 действий"""
    page.goto(BASE_URL + "/login")
    page.fill("#username", os.environ["VISTEST_USER"])
    page.fill("#password", os.environ["VISTEST_PASSWORD"])
    page.click("button[type=submit]")
    page.wait_for_selector("[data-testid=user-menu]")
    page.goto(BASE_URL + "/account")
    visual.assert_screenshot("account.png")
```

Секреты остаются в `os.environ`, в файл не попадают. Если тестов за логином
много — вынесите авторизацию в фикстуру `conftest.py` со `scope="session"` и
переиспользуйте `storage_state`.

## 3.4. Подключение существующего набора тестов

У команды уже есть визуальные тесты: свой `conftest`, свои page objects, свои
эталоны в git, свой способ сравнения. Переписывать это ради нового инструмента
никто не станет — и правильно сделает.

**Ключевое решение: чужой код не разбирается.** Понять шаги чужого теста
статически невозможно — там произвольный Python с фикстурами, наследованием и
условиями. Вместо этого их pytest запускается как есть, а VisTest вклинивается
ровно в одну точку — туда, где скриншот сравнивается с эталоном. Логин,
навигация, ожидания, маркеры, параметризация продолжают работать их кодом, и
знать о нём нам не нужно.

### Подключение

```bash
vistest project add D:\project\aeron-api-tests
vistest project list
```

или вкладка **«Проекты»** в UI: путь → «Осмотреть» → правки → «Подключить».

Осмотр находит и показывает: папки эталонов, каталог визуальных тестов,
интерпретатор, маркеры pytest, переменные окружения из кода, кандидатов на
точку сравнения, наличие Dockerfile. Всё найденное — **предложение**: оно
правится до сохранения. Угадывать молча в чужом репозитории мы не считаем
приличным.

Описание ложится в `.vistest/projects.yaml` — обычный текст, его можно
закоммитить и раздать команде. Секретов там нет: только имена переменных.

```yaml
projects:
  aeron-api-tests:
    name: aeron-api-tests
    root: D:\project\aeron-api-tests
    tests: UiTests/tests/screenshot_tests
    python: D:\project\aeron-api-tests\.venv\Scripts\python.exe
    pytest_args: ["-m", "screenshot"]
    # Чем до их тестов доходит имя браузера, когда прогон запускают в
    # нескольких. `auto` (по умолчанию) — переменная VISTEST_BROWSER всегда,
    # плюс `--browser`, если у них стоит pytest-playwright. `env` — только
    # переменная, их conftest читает её сам. `flag` — только `--browser`.
    # `none` — управлять нельзя: VisTest откажется от многобраузерного прогона
    # и назовёт причину, вместо того чтобы трижды запустить один и тот же
    # браузер и показать покрытие, которого нет.
    browser_option: auto
    baselines:
      - dir: UiTests/tests/screenshot_tests/snapshots_ci
        when: {CI: "true"}
        label: прогон в контейнере / CI
      - dir: UiTests/tests/screenshot_tests/snapshots
        label: локальный прогон
    adapter:
      target: UiTests.pages.base_page.BasePage.assert_screenshot
      name_arg: 0
      page_attr: page
```

### Два режима

| | Когда | Что даёт |
|---|---|---|
| **адаптер** | указана точка сравнения | сравнение движком VisTest прямо во время теста: severity, регионы, классы изменений, DOM-атрибуция, все артефакты |
| **разбор PNG** | точка не указана | их тесты гоняются как есть, потом сопоставляются лежащие на диске пары «эталон / факт» |

Разница существенная. DOM-атрибуцию (`REMOVED button[data-testid="submit"]`)
можно получить только с живой страницы — после прогона её уже нет. Поэтому
режим разбора отвечает «что изменилось», но не «у какого элемента».

**Как работает адаптер.** К их pytest добавляется `-p vistest.adapter`. Плагин
подменяет указанный метод: страница снимается их же драйвером (с нашей
стабилизацией, серией кадров и DOM-снепшотом), сравнение выполняет движок
VisTest, эталон читается из папки их проекта. При расхождении поднимается
`AssertionError` — их тест краснеет ровно так же, как краснел бы от их
собственной проверки.

Маски из их вызова уважаются: если в коде написано
`assert_screenshot("login.png", mask_selectors=[".timer"])`, селектор
добавляется к нашим. Команда писала его не от скуки.

Если перехват не удался, прогон не падает: в лог пишется предупреждение, и
зовётся их оригинальная проверка. Человек запускал тесты, а не наш адаптер.

### Два комплекта эталонов: их и наш

Это, пожалуй, главная развилка при подключении, и решать её надо осознанно.

Эталоны проекта сняты **их** конвейером: их способ ожидания, их параметры
скриншота, их сборка full-page. Захват VisTest работает иначе — замораживает
анимации до первого рендера, подменяет источники времени и случайности, снимает
серию кадров и вычисляет по ним маску нестабильности.

Сравнивать снимок одного конвейера с эталоном другого бессмысленно. Разойдутся
шрифты, тени, момент съёмки — и движок честно покажет расхождения, которых в
приложении нет. Это не дефект движка, это несопоставимые данные.

Поэтому есть два режима:

| | Когда выбирать |
|---|---|
| **эталоны проекта** (по умолчанию) | их снимки сделаны совместимым способом, и вы хотите, чтобы апрув попадал в их git |
| **собственные VisTest** | нужен честный результат сразу; их папка при этом не трогается вообще |

```bash
vistest project baselines my-tests               # что где лежит
vistest project baselines my-tests --use vistest # снимать свои
vistest project baselines my-tests --reset       # удалить свои и снять заново
```

В UI это кнопка «Снять собственные эталоны» в строке «Эталоны» на карточке.

**Как выглядит переход.** После переключения комплект пуст. Первый прогон
снимает эталоны и помечает снимки как `new_baseline` — тесты зелёные, потому
что сравнивать пока не с чем. Регрессы начинает ловить второй прогон.

**Насколько это важно — измерено.** Один и тот же набор из одиннадцати тестов,
один стенд, один движок, одни пороги. На эталонах, снятых VisTest, — 35
сравнений и ноль падений. На эталонах проекта — 18 сравнений и 13 падений.
Отличается только то, чей конвейер снимал эталон. Подробно с оговорками про
размер выборки — [`CASE-STUDY.md`](CASE-STUDY.md).

Отсюда практическое следствие: если первый прогон на эталонах проекта дал
красное почти везде, это скорее всего не поломки в приложении. Посмотрите
заметки о выравнивании — субпиксельные сдвиги вида `dx=-0.54` означают именно
разницу конвейеров.

Собственный комплект разделён по платформам
(`.vistest/external/<проект>/baselines/win-chromium-1x/`): рендер текста в
Windows и в контейнере физически разный, и общего эталона между ними не бывает.
Их правило `snapshots` / `snapshots_ci` здесь не нужно — платформа
определяется сама.

**Пересъёмка.** Кнопка «⟳ Пересоздать эталоны» (или `--update` в командной
строке) перезаписывает весь комплект текущим состоянием приложения. Убедитесь,
что приложение сейчас выглядит правильно: иначе вы закрепите поломку как норму.

`--reset` отличается тем, что удаляет комплект целиком, а не перезаписывает.
Полезно после смены версии браузера или намеренного редизайна, где проще снять
заново, чем разбирать двадцать диффов по одному. Папку проекта `--reset` не
трогает никогда.

### Их тесты видно на вкладке «Tests»

Вкладка показывала ровно то, что сгенерировали мы сами, и для подключённого
набора отвечала «0» при одиннадцати снимках: человек видел, что снимки чем-то
сняты, но чем именно — в интерфейсе не было нигде.

Теперь файлы подключённых проектов там есть — с именем, путём и кодом. **Только
чтение**: это чужой репозиторий, у него свой git и своё ревью, и кнопки
«сохранить» здесь нет и не будет. Кнопка «Run» есть, и запускает она тест **через
его проект** — чужим интерпретатором, из чужого корня и с их conftest; нашим
pytest он упёрся бы в первый же их импорт.

Связь работает в обе стороны: карточка снимка называет тест и даёт его открыть,
а у файла теста есть список снимков, которые он снимает. Список ищется по файлу,
а не по конкретному тесту: параметризация даёт десяток идентификаторов на одну
функцию, и разбивать их на десяток списков незачем.

**Как решается, что файл — тестовый.** Ровно так же, как решает pytest: по двум
стандартным шаблонам `test_*.py` и `*_test.py`, а если проект задал свои
`python_files` в `pytest.ini`, `pyproject.toml`, `tox.ini` или `setup.cfg` — по
ним. Раньше здесь стоял один жёсткий `test_*.py`, и набор, названный по второму
стандартному шаблону (`login_test.py`), давал на вкладке пустоту — при том что
прогон эти тесты находил и снимал по ним эталоны: запускает-то их pytest
проекта, а не мы.

Если не нашлось ничего, вкладка больше не отвечает «No tests yet». Пустой список
имеет ровно три причины — каталог не тот, шаблоны имён не те, файлов правда
нет, — они лечатся по-разному и выглядят одинаково. Поэтому вкладка называет
каталог, в который смотрела, шаблоны, которыми искала, и откуда эти шаблоны
взяты.

**Файлы и тесты — разные числа.** Список показывает ФАЙЛЫ, а свой набор человек
помнит ТЕСТАМИ: шесть строк против одиннадцати эталонов читаются как потеря,
хотя это одиннадцать тестов в шести файлах. Поэтому у каждого файла стоит число
тестов в нём, а заголовок группы называет оба: «6 files · 11 tests». Тесты
считаются по объявлениям и по `python_functions` того же проекта; параметризация
не разворачивается — `def` в файле ровно столько, сколько видно глазами.
Запускать чужой набор ради списка имён вкладка не будет: это чужой код на каждый
заход на экран.

**Что лежит мимо каталога.** Если под корнем репозитория есть подходящие файлы
вне настроенного каталога тестов, вкладка называет их число и первые пути. В
список они не попадают: где лежат тесты, говорит подключение, и подменять его
догадкой нельзя — но промолчать значило бы оставить человека наедине с разницей
между тем, что он знает о своём наборе, и тем, что видит. Обход не заходит в
`node_modules`, `__pycache__`, `venv`, `dist`, `allure-results` и прочие
заведомо чужие ветки, а также в скрытые каталоги: без этого он упирается в
зависимости чужого репозитория — это секунды на каждый запрос и тысячи чужих
файлов в списке, где ждут шесть своих.

### Пустой набор по умолчанию — не ответ

Набор эталонов по умолчанию — собственный набор сервиса, платформа по
умолчанию — платформа его машины. У человека, который только что подключил
проект, не совпадает ни то, ни другое: собственный набор пуст, а эталоны
проекта сняты в docker, тогда как сервис стоит на windows. Экран отвечал
«0 baselines», сборка тестов — «baselines on the platform: 0», и оба ответа
были верны ровно про то место, куда никто не смотрел.

Теперь, пока набор и платформа не выбраны руками, открывается непустое.
Правило узкое намеренно: выбор человека не переписывается никогда, и непустой
набор по умолчанию не подменяется «более полным» — это перекладывание экрана
под ногами. Подменяется только пустое. Счётчик в навигации считает по всей
установке, а не по текущему набору: он отвечает на «есть ли у меня эталоны
вообще».

Сборка тестов из эталонов больше не угадывает вовсе: кнопка «Assemble from
baselines» спрашивает набор и платформу, показывая все наборы установки с
числами сразу. Угадать правильно она не могла, а показать, из чего собирает, —
может. Непустое предвыбрано, пустое видно и не нажимается. В логе первой
строкой стоит, куда смотрели, и если там пусто — где не пусто.

### Собранный тест связан со своими эталонами сразу

«Assemble» собирал тест и оставлял две половины, которые друг о друге не
знают: карточка снимка говорила «теста нет», страница теста — «снимков нет».
Связь появлялась только после первого прогона, потому что писал её прогон.

Теперь она пишется в момент сборки — но **отдельным полем**, `generated_by`, а
не в `source`. Это два разных вопроса: `source` отвечает на «чем снимок БЫЛ
СНЯТ», и переписать его сборкой значило бы соврать про тест, который ещё ни
разу не выполнялся. В списке снимков такая связь помечена «built from it», и
пометка исчезает, когда тест действительно снимет их сам.

Заодно исправлено сравнение, из-за которого связь терялась и у чужих тестов. В
паспорте лежит путь, каким его видел pytest ТОГО прогона — относительно корня,
из которого его запускали, — а спрашиваем мы путём от корня проекта. Для
набора, который гоняют из подкаталога, это `tests/…/login_test.py` против
`UiTests/tests/…/login_test.py`: один файл, записанный двумя способами, и
сравнение строк отвечало «нет». Сравниваются хвосты путей по сегментам, так что
`api/health_test.py` и `ui/health_test.py` остаются разными файлами.

### Связь читается прямо из кода теста

Оба способа выше требуют **события**: связь пишет либо прогон (в момент
съёмки), либо сборка. А набор, снятый чужими тестами до того, как источник
вообще стали записывать, стоял и молчал — при том что код прямым текстом
говорит, какой тест какой снимок снимает:

```python
def test_mailbox(logged_in_page, visual):
    visual.assert_screenshot('mailbox.png')
```

Теперь это читается. Имя снимка берётся первым строковым аргументом
`assert_screenshot`, тест — ближайшим `def` выше; имя из хранилища сходится с
именем из кода по последнему сегменту без расширения (`shop.example/login.png`
и `login` — один снимок). Считается по файлам и кэшируется по их временам, так
что правка теста видна сразу, а не после прогона.

Три правила, без которых это было бы хуже отсутствия связи:

* **записанное не переписывается.** Что снимок был снят, знает прогон; код
  знает только, что он объявлен. Есть запись — она и показывается;
* **имя, собранное на лету** (`f'page_{n}.png'`), не разбирается и не
  угадывается: догадка привязала бы снимок не к тому тесту;
* **два теста на один снимок — это вопрос, а не связь.** Такой снимок остаётся
  непривязанным: показать один из двух значило бы дать человеку ответ, которому
  он поверит.

Практическая польза не в надписи: снимок с источником-тестом **перепроверяется
этим тестом**. Для страницы за входом это единственный верный способ — по
адресу снялась бы форма логина.

### Снять страницу движком VisTest, не заводя ради этого теста

На карточке проекта есть кнопка «Capture a screenshot». Она открывает браузер
на машине сервиса и кладёт снимок в набор VisTest этого проекта — со спекой,
то есть его сразу можно переснять и проверить кнопкой.

Спрашивается ровно то, от чего зависит кадр:

* **адрес** и **имя**;
* **что попадает в кадр** — вся страница, только окно или один элемент по
  селектору. Это и есть формат снимка: длинный отчёт снимают целиком, шапку
  элементом, бесконечную ленту только экраном — Chromium физически не отдаёт
  полотно в тридцать тысяч пикселей;
* **размер окна** — вёрстка у ширины 1440 и 390 разная, и снимок без размера
  ничего не фиксирует;
* **шаги** и **пауза** — почти всё интересное лежит за входом.

Всё это уходит в паспорт снимка, поэтому «Re-capture» возвращает тот же кадр.
Раньше область кадра была одной настройкой на всю установку (`capture.full_page`),
и на снимок её было не поменять: пересъёмка возвращала другой кадр того же
адреса, а разница читалась как изменение страницы. Настройка установки осталась
умолчанием — снимок без области ведёт себя ровно как раньше, иначе появление
поля молча переснимало бы весь накопленный набор по-другому.

### Эталоны проекта остаются на месте

VisTest читает PNG из их папки и при апруве **перезаписывает там же**. Файл
попадает в обычный `git diff` и на обычное ревью — то есть в их привычный
процесс. Второй копии в `.vistest` не появляется: она разошлась бы с первой на
первой же неделе.

Историю версий VisTest здесь не ведёт намеренно — она уже есть и называется git.

Всё, чего в чужом репозитории быть не должно (маска нестабильности, игнор-зоны,
DOM-снепшот, паспорт), лежит в «спутнике» внутри `.vistest/external/<проект>/`.

### Два комплекта эталонов

Рендер шрифтов в Windows и Linux физически разный, поэтому у проектов с
прогоном в контейнере эталонов обычно два: `snapshots/` и `snapshots_ci/`.
Правило выбора описывается условием на переменные окружения и **не
угадывается** в момент прогона:

```bash
vistest project run aeron-api-tests              # snapshots/
vistest project run aeron-api-tests --env CI=true  # snapshots_ci/
```

В UI это две кнопки: «▶ Прогнать» и «▶ Как в CI».

Правила с условиями должны стоять выше безусловного — иначе безусловное
перехватит всё. Автоопределение расставляет их правильно.

### Прогон

```bash
vistest project check aeron-api-tests            # собрать, ничего не запуская
vistest project run aeron-api-tests
vistest project run aeron-api-tests --env CI=true --update
vistest project run aeron-api-tests -- -k login -v
```

Перед прогоном VisTest сам делает `check`: если их тесты не собираются, вы
увидите причину, а не «всего 0, упало 0».

Код возврата `1`, если хоть один снимок разошёлся с эталоном — годится для
гейта в пайплайне. `--json` отдаёт полную картину машинно.

Их вывод показывается как есть, без пересказа: это единственное, по чему видно,
что у них пошло не так.

### Разбор прогона

Прогон подключённого проекта попадает в **ту же историю**, что и свои — вкладка
«Прогоны». Открывается тем же просмотрщиком: шторка между было/стало, onion,
blink, тепловая карта, таблица регионов с подсветкой на скриншоте. Отдельного
просмотрщика для внешних проектов нет намеренно — второй такой же был бы хуже
первого.

Прогон записывается под именем проекта, а не под `default`, поэтому в списке
слева есть переключатель проектов. По умолчанию показываются все.

В историю попадают **все** снимки, а не только упавшие. Прошедший снимок тоже
результат: по нему видно, что именно приняли за норму, и без него в истории
остаётся строчка «pass» без единой картинки.

На карточке проекта под таблицей есть кнопка «→ Открыть с картинками», а в
самой таблице — «Снимок» на каждой строке.

Запись в историю не может уронить прогон: если она почему-то не удалась, в
логе будет предупреждение, а результаты останутся. Отключается флагом
`--no-history`.

### Чужой венв не нужен

Прогон идёт **окружением VisTest**, а не окружением подключённого проекта. Там
уже есть pytest, Playwright и браузеры. Их код импортируется как есть: корень
репозитория добавляется в `PYTHONPATH`, поэтому `from UiTests.pages...`
работает без `pip install -e .` в их проекте.

Это осознанное решение. Чужое виртуальное окружение — обязательство, а не
актив: его может не быть вовсе, оно может быть собрано под другую версию
Python, в нём может не оказаться pytest (частый случай — венв заводили под
линтер), и уж точно в нём нет `vistest`, без которого не подключится
плагин-адаптер. Требовать от команды сначала починить свой венв, чтобы
попробовать инструмент, — верный способ не получить пилот.

Если их зависимостей не хватает, они ставятся **к нам**:

```bash
vistest project check my-tests        # что не импортируется
vistest project deps my-tests         # доставить недостающее
vistest project deps my-tests --all   # весь requirements.txt
```

`check` поднимает их `conftest` и собирает тесты, ничего не запуская. Имя
недостающего модуля берётся из их собственной ошибки, а не угадывается по
`requirements.txt`: имя пакета и имя модуля совпадают далеко не всегда
(`dotenv` → `python-dotenv`, `yaml` → `PyYAML`, `cv2` → `opencv-python`).

`deps` по умолчанию ставит **только недостающее**. `requirements.txt` описывает
весь проект, а нам нужны визуальные тесты: драйвер базы или генератор тестовых
данных им не нужны, зато под свежий Python они часто не собираются — и вся
установка падает на пакете, который в этих тестах не используется.

Версия берётся из их файла, если пакет там закреплён: у команды могут быть
основания на конкретный пин. Если у закреплённой версии нет колеса под текущий
Python, делается вторая попытка без закрепления — и только потом пакет
объявляется пропущенным.

Каждый пакет ставится отдельно. Падение одного не отменяет остальные: список
пропущенного с причинами полезнее, чем «не установилось ничего». Компилировать
из исходников VisTest не пытается — сотня строк вывода компилятора человеку,
нажавшему кнопку, ничего не объясняет.

Если пропущено много и всё с формулировкой «нет готового колеса» — окружение
VisTest собрано на более свежем Python, чем проект. Пересоберите наш venv на
их версии: подойдут ровно те же колёса.

Запустить их венвом всё же можно — в настройках проекта выбирается
интерпретатор. Тогда `vistest` придётся поставить туда самим. Если в указанном
интерпретаторе не окажется pytest, VisTest переключится на своё окружение сам и
скажет об этом в логе — молча падать с «No module named pytest» он не будет.

### Переменные окружения

Пароли к стенду берутся из окружения. VisTest подставляет их в прогон в таком
порядке (ближе к человеку — сильнее):

1. окружение сервиса
2. `.vistest/secrets.env` — заполняется на вкладке «Настройки»
3. `env` в описании проекта
4. `--env K=V` при запуске

Пустое значение означает «переменной быть не должно». Для проектов, которые
выбирают эталоны по наличию `CI`, это единственный способ заставить прогон
вести себя как локальный.

### Про безопасность

Вкладка «Проекты» запускает произвольный процесс на машине сервиса. Это
принципиально мощнее всего остального в API, поэтому по умолчанию она отвечает
**только на локальные запросы**. Открыть наружу — `VISTEST_PROJECTS_UI=all`,
выключить совсем — `VISTEST_PROJECTS_UI=off`.

Отключение проекта (`vistest project rm`) удаляет только запись в реестре.
Файлы проекта не трогаются никогда.

## 4. Как писать тесты

### Минимальный тест

```python
def test_checkout(page, visual):
    page.goto("https://shop.example/checkout")
    visual.assert_screenshot("checkout.png")
```

`page` — стандартная фикстура pytest-playwright. `visual` — фикстура VisTest,
регистрируется автоматически (плагин подключён через entry point).

### Параметры `assert_screenshot`

```python
visual.assert_screenshot(
    "checkout.png",
    clip_selector="#order-summary",     # снять только элемент, не всю страницу
    full_page=False,                    # только видимая область
    mask_selectors=["#promo-banner"],   # ручные маски (обычно не нужны)
    delta_e_threshold=1.5,              # строже по цвету для этого снимка
    fail_severity=40,                   # мягче порог падения
    max_changed_area_pct=0.5,
    ignore_kinds=("noise", "antialias", "moved"),  # игнорировать перемещения
    soft=True,                          # не бросать исключение, вернуть результат
)
```

Возвращается `CompareResult` — можно использовать в собственных проверках:

```python
res = visual.assert_screenshot("page.png", soft=True)
assert not [r for r in res.regions if r.kind is ChangeKind.REMOVED]
```

### Компонент вместо всей страницы

Это главный практический совет. Снимок одного компонента:

- стабильнее — меньше площади, меньше шансов поймать динамику;
- информативнее — понятно, что именно сломалось;
- быстрее — и снять, и сравнить.

```python
def test_pricing_cards(page, visual):
    page.goto(URL)
    visual.assert_screenshot("pricing.png", clip_selector="#pricing")
```

Полностраничные снимки полезны как «сеть безопасности», но не должны быть
единственным видом проверки.

### Мягкий режим: собрать все различия сразу

По умолчанию первый же дифф бросает исключение и прячет остальные. Фикстура
`visual_soft` собирает всё и падает один раз в конце:

```python
def test_landing_sections(page, visual_soft):
    page.goto(URL)
    visual_soft.assert_screenshot("header.png", clip_selector="header")
    visual_soft.assert_screenshot("hero.png", clip_selector="#hero")
    visual_soft.assert_screenshot("footer.png", clip_selector="footer")
```

### Адаптив и темы

Разные ширины и темы — это разные эталоны, отдельные снимки:

```python
@pytest.mark.parametrize("width,label", [(390, "mobile"), (768, "tablet"), (1440, "desktop")])
def test_responsive(page, visual, width, label):
    page.set_viewport_size({"width": width, "height": 900})
    page.goto(URL)
    visual.assert_screenshot(f"landing-{label}.png")


def test_dark_theme(page, visual):
    page.goto(URL)
    page.click("#theme-toggle")
    visual.assert_screenshot("landing-dark.png")
```

### Сравнение двух файлов без браузера

Для отладки движка или сравнения макета с реализацией:

```bash
python run.py compare design.png implementation.png
vistest compare expected.png actual.png -o diff/ --preset strict
```

## 5. Жизненный цикл эталона

### Где лежат

```
.vistest/baselines/<платформа>-<браузер>-<масштаб>/<проект>/<имя-снимка>/
    baseline.png      эталон
    stability.png     накопленная маска нестабильности
    dom.json          DOM на момент апрува
    meta.json         паспорт: адрес, размер окна, селектор, шаги, версия,
                      git sha, кто и когда заапрувил, ignore-боксы
    history/v3.png    предыдущие версии
```

Пример ключа платформы: `win-chromium-1x`, `linux-chromium-1x`, `docker-chromium-1x`.

**Эталоны разных платформ не взаимозаменяемы.** Рендер текста в Windows и Linux
отличается физически, общий эталон между ними невозможен. Локально вы
сравниваетесь со своим набором, CI — с докерным.

### Проекты

Имя снимка — это ключ к эталону. Если тестировать два приложения из одного
каталога, их `login.png` схлопнутся в один эталон, и вы получите дифф «главная
одного проекта против главной другого».

Поэтому проект — часть имени: `shop.example/login.png`. При записи он
определяется по домену автоматически, можно задать явно:

```bash
python run.py record https://shop.local  --project shop
python run.py record https://admin.local --project admin
```

В коде проект задаётся один раз на файл — генератор делает это сам:

```python
PROJECT = "shop.example"


@pytest.fixture(autouse=True)
def _vistest_project(visual):
    visual.project = PROJECT


def test_login(page, visual):
    page.goto(BASE_URL + "/login")
    visual.assert_screenshot("login.png")      # → shop.example/login.png
```

В UI проекты — вкладки над сеткой эталонов: фильтр, проверка и удаление
работают в рамках выбранного проекта.

Эталоны без проекта (снятые раньше) продолжают работать — мигрировать ничего
не нужно.

### Пересборка тестов

Файлы тестов собираются **из паспортов эталонов**, а не из последней сессии
записи — по файлу на проект:

```bash
python run.py codegen                       # все проекты текущей платформы
python run.py codegen --project shop --out tests/
```

То же самое — кнопка «⚙ Собрать тесты» на вкладке «Эталоны».

Это важно по двум причинам. Во-первых, запись второго проекта больше не
затирает тесты первого: файлы разные. Во-вторых, тесты можно пересобрать когда
угодно — после правки адресов и шагов в UI, после удаления снимков, на новой
машине — ничего не переснимая.

Эталоны без заданного адреса в тесты не попадают: из чего строить `page.goto`,
неизвестно. Задайте им url кнопкой «Адрес».

### Создание

Происходит автоматически при первом прогоне: тест помечается `NEW_BASELINE`,
эталон сохраняется. **Обязательно посмотрите созданный эталон глазами** —
`.vistest/runs/<run_id>/<имя>/actual.png`. Если вы заапрувили сломанную
страницу, все последующие прогоны будут сравниваться с поломкой.

### Обновление

```bash
# все эталоны
python run.py update

# только конкретный тест
python run.py update examples/test_demo_visual.py::test_landing_page

# через pytest напрямую
pytest tests/ --vistest-update

# один снимок из CLI
vistest approve checkout.png --actual .vistest/runs/<run_id>/checkout_png/actual.png
```

Или в UI кнопкой «✓ Принять как эталон» — так надёжнее, потому что перед этим
вы видите дифф.

Каждое обновление увеличивает `version` и копирует предыдущий эталон в
`history/`, так что откат — это копирование файла обратно.

### В git

Главное правило: **эталоны коммитятся, всё остальное из `.vistest` — нет.**
Без эталонов в репозитории сравнивать не с чем: у коллег и в CI их просто не
будет, и первый же прогон молча создаст новые из текущего состояния — включая
сломанное.

`.gitignore` в проекте уже настроен: артефакты прогонов, база сервиса, модели и
секреты исключены, `.vistest/baselines/` явно разрешён.

Что **никогда** не должно попасть в репозиторий:

| Путь | Почему |
|---|---|
| `.vistest/secrets.env` | логины и пароли |
| `.vistest/state/` | сохранённые сессии — по сути действующий доступ к стенду |
| `.vistest/*.db` | локальная история прогонов, у каждого своя |
| `.vistest/runs/`, `.vistest/artifacts/` | мегабайты PNG на каждый прогон |
| `models/*.onnx` | десятки мегабайт, пересоздаются скриптом |

Для секретов есть шаблон — скопируйте и заполните:

```bash
cp .vistest/secrets.env.example .vistest/secrets.env
```

PNG в git растут: сотня полностраничных снимков — это уже сотни мегабайт, и
каждое обновление добавляет копию в историю навсегда. Если набор большой,
включите LFS **до** первого коммита эталонов:

```bash
git lfs install
git lfs track ".vistest/baselines/**/*.png"
```

и раскомментируйте соответствующую строку в `.gitattributes`. Учтите: без
установленного git-lfs у коллег клон получит текстовые заглушки вместо
картинок — это решение для всей команды, поэтому по умолчанию выключено.

## 5.0. Страница снимка

У каждого снимка есть своя страница: `#/snapshot/<набор>/<платформа>/<имя>`.
Попасть на неё можно тремя путями — щёлкнуть по имени на карточке во вкладке
«Baselines», выбрать «Open the snapshot page» в меню «⋯», или из разбора
падения по ссылке под заголовком.

Что там есть:

* **Эталон** — картинка, версия, кто и когда принял, размер;
* **Спека целиком** — адрес, размер окна, селектор, пауза и шаги. Именно она
  делает снимок запускаемым: без адреса его нельзя ни переснять, ни проверить.
  Пустое поле **снимает** значение (не то же самое, что пустая строка);
* **Ignore-зоны** — выделяются мышью прямо по эталону. Зона принадлежит
  **снимку**, а не одному сравнению, поэтому действует во всех прогонах.
  Часы, карусель, случайный аватар — сюда;
* **История проверок** по всем прогонам с вердиктом, severity и веткой; клик
  открывает конкретное сравнение;
* Кнопки **«Check now»** (прогнать только этот снимок) и **«Re-capture»**
  (открыть страницу заново и сделать снятое новым эталоном — предыдущая версия
  уходит в историю, откат остаётся возможен).

Зоны и спека применяются со следующего прогона; уже записанную историю они не
меняют.

## 5.0.1. Чем снят снимок

У снимка есть паспорт, и в нём записано, **чем именно** он снят: тестом или
адресом. От этого зависят кнопки «Check» и «Re-capture».

Почему это оказалось важно. Раньше кнопки появлялись, как только у снимка был
адрес, и делали ровно одно — грузили этот адрес. Для страниц, открытых с улицы,
честно. Для всего, что лежит **за входом** — а это большинство страниц любого
внутреннего продукта, — это означало снять форму логина: прогон, который «ничего
не нашёл», или эталон, переписанный страницей входа. Заметить подмену можно было,
только открыв картинку.

Теперь:

| Чем снят | Что делает «Check» | Что делает «Re-capture» |
|---|---|---|
| тестом | прогоняет **тот же тест** — с его логином, переходами и подготовкой данных | то же, и принимает картинку как эталон |
| адресом | грузит адрес и сравнивает | грузит адрес и переписывает эталон |
| ничем | говорит, чего не хватает | — |

Связь записывается **в момент съёмки**, из `PYTEST_CURRENT_TEST` — переменной,
которую ставит сам pytest. Это единственный канал, работающий одинаково для наших
тестов и для чужих: адаптер подключается к чужому pytest снаружи и не знает
ничего про их фикстуры и базовые классы, а переменная есть и там. Рядом
записывается ключ проекта: идентификатора теста мало, надо знать, **где** его
искать — чужой тест запускается чужим интерпретатором, из чужого корня и с их
conftest.

Снимки, снятые до появления этой записи, честно говорят «source not recorded».
Написать про них «снят по адресу» было бы неправдой: половина снята тестами, и
предложить проверить их адресом — предложить снять форму входа. Один прогон, и
связь появляется сама.

Прогон одного снимка через тест — это прогон **одного** теста, а не всего набора:
идентификатор заменяет цель pytest, а не добавляется к ней.

## 5.1. Отчёт для тикета

Разбор регресса не заканчивается в интерфейсе: заводится тикет, и в него надо
что-то вложить. Ссылка на `localhost:8420` бесполезна — её не откроет ни
разработчик на другой машине, ни тестировщик через полгода, когда прогон уже
вычищен ретенцией.

```bash
python run.py report                    # последний прогон
python run.py report .vistest/runs/2026… -o bug-1234.html
python run.py report --open
```

Получается **один файл**: картинки внутри как data-URI, стили внутри, скрипт
внутри. Ни одного внешнего запроса — открывается двойным кликом на машине без
сети. Это то же требование, что и §1.1 позиционирования: инсталляция в закрытом
контуре не ходит наружу ни за чем, включая шрифты и библиотеки графиков.

Внутри: упавшие снимки первыми и по убыванию severity, метрики, таблица
регионов с классами и селекторами, все артефакты (разметка, наложение, тепловая
карта). Клик по картинке открывает её в натуральную величину — на
полностраничных полотнах вписанная по ширине картинка нечитаема, а именно в
ней и надо разглядеть, что поехало.

Печать в PDF работает: под `@media print` включается светлая тема и запрет
разрывов внутри карточек.

В UI — кнопка «⤓ Отчёт для тикета» в шапке прогона. В CI — шаг `after_script`
в примере для GitLab.

## 5.2. Эталон на ветку

Выключено по умолчанию: команде с одной веткой режим не даёт ничего, а вопросов
добавляет. Включается в «Settings → Baselines per branch».

**Зачем.** Эталон был один на платформу, а веток много. Кто-то намеренно
переверстал форму в своей ветке, посмотрел дифф, принял его как новую норму — и
main начал падать на том же снимке. Обратный случай не лучше: main обновили, а в
ветке, где эта часть страницы ещё старая, всё покраснело.

**Как устроено.** Ветка не получает свой набор целиком — она получает
**наложение**: только те снимки, которые сама переопределила. Остальное
наследуется.

```
читаем   →  из ветки, если она этот снимок переопределила, иначе из основного набора
пишем    →  ВСЕГДА в ветку
```

Отсюда главное свойство: апрув на ветке физически не может изменить основной
эталон. Панель решения говорит это прямо — «…on branch feature/pay», и отдельно
предупреждает, если снимок пока унаследован.

Прогон **без ветки** — например, снятие эталона по URL прямо из интерфейса —
считается основным. Заводить ему отдельное наложение значило бы развести два
набора там, где человек видит один.

**После слияния.** Ветку надо влить: «Promote to main» на карточке ветки в
настройках. Без этого шага ветка становится ловушкой — решение принято, ветка
слита, а main падает на том же снимке, потому что решение осталось в наложении,
которое уже никто не читает. Картинка переносится обычной записью, то есть
прежняя уходит в историю основного набора и откат остаётся возможен.

«Discard» — противоположное решение: выбросить наложение, не трогая основной
набор. Это две разные кнопки нарочно, а не одна с выбором.

| Роут | Что делает |
|---|---|
| `GET /api/branches` | ветки, у которых есть свои эталоны |
| `POST /api/branches/promote` | влить в основной набор (`delete_after` — сразу и выбросить) |
| `DELETE /api/branches/{branch}` | выбросить наложение |
| `GET/PUT /api/settings/branches` | режим и имя основной ветки |

## 5.3. Уведомления о непросмотренных падениях

Всё остальное в VisTest устроено так, что человек приходит и смотрит. Это
работает ровно до первого дня, когда он не пришёл: двенадцать падений лежат
третьи сутки, эталон устаревает, а следующий прогон краснеет уже на них — и
никто не знает, что смотреть надо было позавчера.

Настраивается в «Настройках»: включить, вписать URL вебхука, выбрать порог «жду
дольше стольких часов» (по умолчанию сутки). Кнопка **«Send now»** отправляет
дайджест немедленно — без неё первая проверка адреса случилась бы через сутки, а
опечатка в нём выглядит ровно как «разбирать нечего», то есть как тишина.

**Куда.** В вебхук. Один URL, обычный `POST` с JSON, никаких клиентов на каждую
площадку и никаких токенов у нас. Slack, Mattermost и Telegram-мосты принимают
поле `text` как есть; остальные разбирают `count` и `snapshots` из того же тела.
Почта сюда намеренно не входит: SMTP — это сервер, логин, пароль и TLS в
настройках, вчетверо больше поверхности ради канала, который в командах всё
равно проигрывает чату.

**Когда молчит — и это важнее, чем когда говорит:**

* разбирать нечего — не пишет. Ежедневное «ожидает 0» приучает не открывать
  канал, и в день, когда написать будет что, его тоже не откроют;
* список не изменился — не пишет. Повторять один и тот же перечень каждые сутки
  значит превратить его в фон; про застрявший разбор скажет строка «самое старое
  ждёт третьи сутки» в следующем сообщении, которое всё-таки уйдёт;
* падение свежее порога — не пишет. Разбор в тот же день это нормальная работа,
  а не долг;
* один снимок, красный в двадцати прогонах подряд, — это **один** вопрос, а не
  двадцать: считается по снимкам, и берётся последнее сравнение каждого.

**О чём не молчит.** Сломавшийся вебхук — худший из отказов: канал тих, и тишина
читается как «всё разобрано». Поэтому причина последней неудачи хранится и
показывается прямо в настройках.

```bash
python -m vistest.cli notify --dry-run     # показать текст и не отправлять
python -m vistest.cli notify --force       # отправить, даже если список тот же
```

Команда существует для двух случаев: посмотреть, что именно уйдёт в чат, и
повесить рассылку на чужой планировщик там, где сервис поднимают по требованию.
Внутри работающего сервиса её никто не вызывает — там тикают собственные часы
(`VISTEST_NOTIFY_TICK_S`, по умолчанию 300 секунд; `0` выключает).

| Роут | Что делает |
|---|---|
| `GET/PUT /api/settings/notifications` | вебхук, порог и признак «включено» |
| `POST /api/settings/notifications/test` | отправить дайджест немедленно |

## 5.4. Что изменил этот мерж

Прогон отвечает на вопрос «что красное сейчас». Перед мержем задают другой —
**что сломала именно эта ветка**, — и это не одно и то же.

Разница дорогая. В ветке двадцать падений, восемнадцать из них были красными и
на мастере: они не про эту ветку. Человек разбирает все двадцать, устаёт на
пятом и дальше принимает не глядя — и ровно те два, ради которых всё
затевалось, уезжают в мастер вместе с восемнадцатью чужими.

Кнопка **«⇄ What changed»** в карточке прогона открывает разбор двух прогонов
по адресу `#/diff/<этот>/<с чем сравнить>`. Второй номер необязателен: без него
берётся предыдущий прогон того же проекта и той же платформы, то есть «что
изменилось с прошлого раза». Адрес постоянный — ссылку кладут в MR так же, как
кладут ссылку на прогон.

Снимки раскладываются по тому, **как изменилось состояние**:

| Группа | Что это |
|---|---|
| **Broke here** | было зелёным, стало красным — ответ на исходный вопрос |
| **No longer checked** | снимка нет в новом прогоне вовсе |
| **Red in both** | не эта ветка; но рост severity — уже она |
| **New snapshots** | ломаться было нечему, они просто появились |
| **Fixed** | было красным, стало зелёным |
| *unchanged* | только счётчик — сто совпавших строк никто не читает |

Отдельно стоит **No longer checked**, и это самая тихая поломка из всех.
Удалённый тест, переименованный снимок, упавшая до съёмки фикстура — во всех
трёх случаях снимок просто исчезает из прогона. Ни одно падение при этом не
показывается, и «в ветке ничего не красное» становится правдой, которая ничего
не значит. Ошибка съёмки (`error`) по той же причине считается красным, а не
«нет данных»: снимок проверялся и перестал.

Разобранное падение остаётся в **Broke here** — решение не отменяет факта
поломки. Отдельно считается «сколько из них ещё без решения»: убирать
разобранное из списка значило бы менять историю задним числом (вчера ветка
сломала три снимка, сегодня один, хотя код тот же).

**Когда сравнивать нельзя.** Если прогоны мерялись против разных наборов
эталонов, в разных каталогах, на разных платформах или база новее
сравниваемого — над таблицей появляется предупреждение. «Сломалось» в таких
случаях может означать «поменялась точка отсчёта», а не «поменялся код», и
красивый список без оговорки отправил бы человека искать коммит, которого нет.

Чего здесь **нет намеренно** — сравнения картинок между прогонами. Соблазн
очевидный: показать «дифф диффов». Но пиксельная разница между двумя
скриншотами разных прогонов складывается из настоящей разницы и из шума стенда,
и разделить их без эталона нечем — получилась бы картинка, которая выглядит как
ответ, а ответом не является. Сравниваются вердикты, то есть решения, уже
принятые движком против эталона.

| Роут | Что делает |
|---|---|
| `GET /api/runs/{id}/diff` | сравнить с предыдущим прогоном |
| `GET /api/runs/{id}/diff?base=<id>` | сравнить с конкретным |

## 6. Тест упал — что делать

### Читаем сообщение

```
Visual mismatch: checkout.png
  SSIM=0.99412  ΔE00 mean=14.82 p95=31.20
  changed area=0.412%  (48320/11712000 px)
  max severity=71.4  regions=2 (suppressed=5)
  alignment applied: dx=+0.40 dy=-0.15
    [removed  ] sev= 71.4 @(40,1204) 260x52 ΔE=18.3  button[data-testid="checkout-submit"] "Оформить заказ"
    [color    ] sev= 28.1 @(612,340) 180x24 ΔE=9.1  span.price
  note: Причина падения: severity 71.4 ≥ 25.0
```

Что здесь читать:

- **severity** — насколько серьёзно (0–100). Сортировка регионов по ней.
- **класс** — `removed` почти всегда баг, `moved` часто безобиден,
  `color` может быть намеренным редизайном.
- **селектор и текст элемента** — сразу понятно, что именно сломалось.
- **suppressed=5** — пять регионов отфильтрованы как шум. Если тест упал
  «непонятно на чём», загляните в `result.json`, там они с причинами.
- **note** — точная причина падения по политике.

### Смотрим артефакты

Лежат в `.vistest/runs/<run_id>/<имя-снимка>/`:

| Файл | Отвечает на вопрос |
|---|---|
| `boxes.png` | что изменилось — рамки с классом и severity |
| `heatmap.png` | насколько сильно — тепловая карта ΔE00 |
| `onion.png` | точное совмещение: красное было, голубое стало. Видно расхождение в 1px |
| `blink.gif` | мигание было/стало — глаз ловит мельчайшие различия |
| `side_by_side.png` | было \| стало \| разметка одним кадром |
| `regions/*.png` | крупный план каждого региона с увеличением |
| `result.json` | все метрики машиночитаемо |

Если сомневаетесь — смотрите `blink.gif`. Это самый чувствительный способ.

### Решаем, что это

| Ситуация | Действие |
|---|---|
| Настоящий баг | чинить код |
| Намеренное изменение дизайна | обновить эталон (`run.py update` или кнопка в UI) |
| Шум, который движок не отфильтровал | см. [раздел 8](#8-борьба-с-нестабильностью) |
| Изменение вне зоны интереса | «игнорировать область» в UI, или `clip_selector` на нужный кусок |

### В Allure

Если установлен `allure-pytest`, все артефакты прикрепляются к упавшему тесту
автоматически — отдельных действий не требуется:

```bash
pytest tests/ --alluredir=allure-results
allure serve allure-results
```

## 7. Настройка порогов

### Пресеты

```bash
python run.py test --preset strict
pytest tests/ --vistest-preset loose
```

| Пресет | ΔE00 | fail_severity | Изм. площадь | Когда |
|---|---|---|---|---|
| `strict` | 1.2 | 10 | 0.02% | дизайн-система, компоненты в изоляции |
| `balanced` | 2.3 | 25 | 0.15% | по умолчанию |
| `loose` | 4.0 | 45 | 0.8% | страницы с контентом от CMS |

### Из интерфейса

Порог падения и порог по площади правятся на вкладке «Settings». Значение
хранится в базе сервиса, а не в `vistest.yaml`: конфиг лежит в git и описывает
проект, а порог принадлежит инсталляции — переписывать чужой версионируемый
файл сервис не должен.

Кто кого перекрывает, по возрастанию силы:

```
дефолт/пресет  →  vistest.yaml  →  глобально в UI  →  на проект в UI
```

Рядом с каждым числом интерфейс пишет, откуда оно взялось: «from vistest.yaml»,
«set here, for everyone», «set here, for this project». Кнопка «Back to
vistest.yaml» снимает переопределение — это не то же самое, что поставить ноль:
ноль здесь осмысленное значение «падать на любом видимом различии».

Куда ставить порог, отвечает гистограмма severity на вкладке «Metrics»: провал
между двумя скоплениями — это и есть его место.

Менять может только администратор: порог общий, и тихо сдвинутый он меняет
вердикты чужих прогонов. Изменение попадает в аудит.

Настройка действует и на прогоны сервиса, и на прогоны подключённых проектов —
до чужого pytest значения доезжают переменными окружения
(`VISTEST_FAIL_SEVERITY`, `VISTEST_MAX_CHANGED_AREA_PCT`).

### vistest.yaml

Лежит в корне проекта, ищется вверх по дереву до `.git`. Ключевые параметры:

```yaml
preset: balanced

diff:
  delta_e_threshold: 2.3     # ΔE00. 1.0 — предел различимости, 2.3 — общепринятый JND
  ssim_threshold: 0.90       # структурный порог
  require_consensus: true    # пиксель значим, только если И цвет, И структура

  max_align_shift_px: 8.0    # больше — считаем регрессом лейаута, а не шумом
  min_region_px: 24          # пикселей МАСКИ (не площади bbox)

  fail_severity: 25.0        # падаем, если хоть один регион серьёзнее
  max_changed_area_pct: 0.15 # либо суммарно изменено больше
  above_fold_px: 900         # первый экран важнее
  above_fold_weight: 1.5
  moved_severity_scale: 0.35 # перемещения менее критичны, чем изменения
  ignore_kinds: [noise, antialias]
  fail_on_size_change: true
```

### Как подбирать

Не «на глаз по одному упавшему тесту», а через бенчмарк:

```bash
python tests/benchmark.py --preset balanced
```

Меняете порог → прогоняете → смотрите, не начали ли проходить SIGNAL-кейсы
(пропуск регресса) или падать NOISE-кейсы (ложное срабатывание). Ложные
срабатывания дороже пропусков: от них команда перестаёт верить тестам и
начинает аппрувить всё подряд.

### Порог на отдельный снимок

Уровней три: `vistest.yaml` → проект → **снимок**. Третий появился потому, что
двух не хватало: один шумный дашборд заставлял ослаблять порог для всего
набора — то есть чинить один снимок ценой чувствительности всех остальных.

Правится на странице снимка, в блоке «Thresholds for this snapshot». Рядом с
каждым полем написано, откуда действующее значение: `from the config`,
`from the global`, `from the project` или `set here`. Без источника число на
экране не отвечает на вопрос, который человек и задаёт: «это я тут выставил или
так везде», — а от ответа зависит, где чинить.

Пустое поле значит «как у всех», и унаследованное значение стоит в подсказке.
Подставлять его прямо в поле было бы удобнее на вид и хуже по сути: тогда «здесь
ничего не задано» и «здесь задано ровно то же» выглядят одинаково, а это разные
вещи — второе не поедет за общей настройкой, когда её изменят.

Ноль — осмысленное значение («падать на любом видимом различии»), а не «не
задано». Снять переопределение можно, очистив поле.

Порог снимка живёт в его паспорте (`meta.json`), а не в базе, и это осознанно:
он обязан ехать вместе с эталоном — в наложение ветки, в спутник чужого проекта,
в архив.

### Приоритет настроек

Аргумент `assert_screenshot` → `--vistest-preset` → `vistest.yaml` →
переменные окружения → дефолт.

Переменные окружения:

```
VISTEST_ROOT=.vistest
VISTEST_API_URL=http://localhost:8420
VISTEST_PROJECT=my-shop
VISTEST_UPDATE_BASELINES=1
VISTEST_PERCEPTUAL=1
VISTEST_RUN_ID=<id>
VISTEST_IN_DOCKER=1
ANTHROPIC_API_KEY=...        # только для LLM-каптионера
```

## 7.1. Пересъёмка при падении

Визуальные тесты умирают не от отсутствия интеграций, а от того, что через месяц
красному перестают верить и жмут «принять» не глядя. Одна анимация, один
спиннер, одна подгрузка шрифта — и набор краснеет через раз.

Логика лечения давно доказана внутри [`doctor`](#8-борьба-с-нестабильностью): он
грузит одну и ту же неизменную страницу несколько раз, и любое расхождение между
загрузками ложное **по построению**. Теперь та же логика работает внутри
прогона, но только там, где что-то упало:

1. снимок упал — снимается **второй кадр** той же страницы;
2. то, что дрожит между двумя кадрами, уходит в маску нестабильности;
3. вердикт пересчитывается — по **первому** кадру, с расширенной маской.

Второй кадр здесь не замена картинки, а **свидетель**. Взять его как результат
значило бы выбирать снимок поудачнее, пока не позеленеет; поэтому сравнивается
по-прежнему первый, и `actual.png`, который человек открывает, — тоже первый.

Подавляется не вердикт, а **конкретные области**. Дрожал спиннер — в маску уйдёт
только спиннер, а съехавшая шапка останется красной: между двумя кадрами она
никуда не дрожала. Устойчивый регресс спрятать таким образом нельзя — устойчивый
это ровно тот, который воспроизводится.

**Честная граница.** Мерцающую поломку — ту, что проявляется через раз, — два
кадра от мерцающего шума отличить не могут. Не могут в принципе, ни здесь, ни у
человека. Поэтому зелёный в таком случае не молчит:

```
Failed on the first capture and passed on the second: 2.4% of the page does not
hold still. The difference did not reproduce, so it is noise — but this snapshot
is unstable, and that is worth fixing at the source.
```

Для недетерминированного рендера это ровно тот текст, который нужен: чинить надо
рендер, а не картинку. А найденная нестабильность уходит в накопленную маску
снимка — второй раз за тот же спиннер платить не придётся.

Платится один лишний кадр и только за упавшее; прошедшие снимки не дорожают.
Выключается `capture.retry_on_fail: false` в `vistest.yaml` — законный выбор
там, где важнее время прогона, а не тишина.

## 8. Борьба с нестабильностью

### Сколько шума в вашем проекте: `vistest doctor`

Прежде чем настраивать маски и пороги, стоит выяснить, с чем вы имеете дело.

```bash
python run.py doctor https://my-app.local
python run.py doctor https://my-app.local --runs 5
python run.py doctor --name checkout.png          # адрес возьмётся из паспорта эталона
```

Страница грузится N раз подряд, **каждый раз в чистом контексте браузера**.
Это принципиально: перезагрузка в том же контексте переиспользует кэш шрифтов
и картинок и прячет ровно тот шум, ради которого команда и запускается — в CI
контекст всегда холодный.

Между загрузками ничего не менялось, значит любое расхождение ложное по
построению. Отсюда прямая и честная цифра: сколько из N−1 пар упало бы, если
бы это был обычный прогон — без подавления и с подавлением VisTest.

```
=== Шум проекта: https://my-app.local ===
  загрузок: 4 (каждая в чистом контексте), размер 1440×3820

Ложные падения на неизменённой странице
  без подавления         ████████████ 3 из 3   (100%)
  с подавлением VisTest  ············ 0 из 3   (0%)
  максимальная severity: 68.4 → 0.0

Нестабильные пиксели
  внутри одной загрузки    3.10%  анимации, таймеры, canvas — маскируются автоматически
  между загрузками         0.42%  шрифты, lazy-load, случайный контент — вот это и роняет CI

Что именно шумит
   1. 3/3 прогонов  [text    ] sev= 61.0  подавлен
      .header__clock  "12:41:07"
      дата или время — включите capture.determinism либо замаскируйте блок

✓ Проект пригоден для визуального тестирования как есть: на неизменённой
  странице VisTest не падает ни разу.
```

**Две метрики шума меряют разное, и лечатся они по-разному:**

| | Что это | Чем ловится |
|---|---|---|
| внутри одной загрузки | анимация, спиннер, таймер, canvas | серия кадров подряд (`capture.stability_shots`) — автоматически |
| между загрузками | шрифты, lazy-load, случайный контент, дата, порядок ответов сети | внутрикадровая маска его **не видит**: каждый отдельный снимок идеально стабилен |

Второй вид и роняет прогоны в CI. Именно поэтому `doctor` грузит страницу
заново, а не переснимает одну и ту же вкладку.

**Код возврата:** `0` — на неизменённой странице падений нет, проект пригоден;
`1` — сначала почините шум. Годится для гейта в пайплайне.

**Артефакты** ложатся в `.vistest/doctor/`: `noise.png` — карта того, что
разошлось между загрузками (белым), `report.json` — те же цифры машинно.
`--json` печатает отчёт в stdout, `--out DIR` меняет каталог.

**В интерфейсе** — вкладка «Диагностика»: поле для адреса, число загрузок,
размер окна и необязательный селектор. Результат рисуется полосами (сколько
упало бы без подавления и с ним), таблицей нестабильных пикселей и списком
источников — каждый с подсказкой, чем лечится. Карта шума открывается по
кнопке. Последний отчёт подтягивается при открытии вкладки, чтобы не гонять
измерение заново ради того, чтобы вспомнить цифры.

На той же вкладке — проверка окружения: версия Python, зависимости, docker,
git, число эталонов по платформам и то, откуда загружен пакет `vistest`
(копия в `site-packages` означает, что правки кода до сервиса не доезжают).

На карточке подключённого проекта есть кнопка «≈ Измерить шум стенда» — она
ведёт сюда же с подставленным адресом.

Если `doctor` показывает высокий процент — не начинайте писать тесты. Сначала
разберитесь с источниками из списка: инструмент, который падает на
неизменённой странице, бесполезен независимо от качества движка.

### Что работает автоматически

Ничего настраивать не нужно, это включено по умолчанию:

1. **Stability-маска.** Делается 3 снимка подряд с интервалом 120 мс. Пиксели,
   различающиеся между ними, не могут быть регрессом — это часы, спиннеры,
   canvas, случайные аватары. Маска копится между прогонами: увиденное однажды
   дрожание запоминается навсегда.
2. **Заморозка CSS** — анимации, транзишены, курсор, скроллбары, `scroll-behavior`.
   Ставится через `add_init_script`, то есть до первого рендера, а не после
   навигации, когда анимации уже отыграли.
3. **Детерминизм** — `Math.random` с фиксированным сидом, замороженный `Date.now`,
   `performance.now`. Без этого «случайный» баннер даёт дифф в каждом втором прогоне.
4. **Авто-маски** — `video`, `canvas`, `iframe`, элементы с активной анимацией,
   `[data-vistest="ignore"]`.
5. **Прогрев lazy-load** — страница прокручивается сверху донизу перед снимком,
   ожидаются шрифты и картинки.

### Ручные средства, если автоматики не хватило

**Разметка в HTML** — самый чистый способ:

```html
<span data-vistest="ignore">build 8f2a91c</span>
```

**Селекторы в тесте:**

```python
visual.assert_screenshot("page.png", mask_selectors=["#live-rate", ".ad-slot"])
```

**Глобально в конфиге:**

```yaml
capture:
  mask_selectors: ["#chat-widget", "[data-testid='timestamp']"]
  stability_shots: 5          # больше кадров = точнее детект динамики
  stability_delay_ms: 250     # для медленной анимации
```

**Область в UI** — кнопка «игнорировать эту область» на регионе диффа.
Записывается в `meta.json` эталона навсегда.

### Как найти проблемные снимки

Дашборд метрик (вкладка «Метрики» в UI) показывает список нестабильных
снепшотов: сколько прогонов, сколько падений, сколько из них человек
заапрувил как «всё нормально». Это готовый бэклог — каждая строка либо просит
маску, либо просит удалить бесполезный снимок.

Если при захвате больше 25% пикселей оказались нестабильны, в заметках прогона
появится предупреждение: страница слишком динамична, сравнивать её целиком
малоинформативно — нужно резать на компоненты.

## 9. Сервис, UI и метрики

### Запуск

```bash
python run.py ui                        # 127.0.0.1:8420, откроет браузер
python run.py ui --port 9000 --no-browser
vistest serve --host 0.0.0.0 --port 8420
```

### Первый вход

Откройте адрес сервиса — форма всё скажет сама. На свежей инсталляции она
предлагает завести **первого администратора**; аккаунт, созданный в этот момент,
получает роль `admin`, и форма закрывается навсегда.

На машине инженера (`python run.py ui`) ничего не спрашивается вовсе: пока
пользователей нет, сервис работает в локальном режиме, как и раньше. Завести
администратора можно в любой момент — пункт «Create an administrator…» в меню
профиля.

Дальше есть два пути пустить к себе людей:

* **Заявка.** Человек открывает адрес, жмёт «Request access», заводит логин и
  пароль. Войти по заявке нельзя: она попадает в очередь к администратору
  («Настройки» → «Access requests»), и тот одобряет её **вместе с ролью**.
  Счётчик заявок висит на пункте «Settings» в меню — без него очередь была бы
  чёрным ящиком. Выключается переключателем «Open registration».
* **Приглашение.** Одноразовая ссылка с заранее выбранной ролью — «Настройки» →
  «Invites». Годится, когда список людей известен заранее.

Если инсталляция смотрит в открытую сеть, задайте `VISTEST_SETUP_TOKEN` — тогда
форма первого администратора спросит его, и занять инсталляцию сможет только
тот, у кого он есть. Подробности и честная оценка рисков — в
[docs/SECURITY.md](SECURITY.md).

Потерян доступ ко всем администраторам:

```bash
vistest user setup-reopen     # только с машины сервиса
vistest user pending          # посмотреть очередь заявок
vistest user approve vic --role reviewer
```

### Роли и права на отдельные проекты

Ролей три, и глобальная роль отвечает на вопрос «что человек может **везде**»:

| Роль | Что можно |
|---|---|
| `viewer` | смотреть прогоны, сравнения, эталоны |
| `reviewer` | принимать и отклонять падения, снимать и переснимать эталоны, запускать наборы |
| `admin` | всё, плюс люди, приглашения, удаление эталонов, массовая уборка |

Пока набор один, этого хватает. Как только к сервису подключён второй,
`reviewer` начинает означать «может переписать эталон **любого** проекта» — а
утверждение необратимо: оно меняет то, с чем сравнивают дальше, и на экране
свой набор от чужого ничем не отличается. Человек, отвечающий за витрину,
одним нажатием меняет точку отсчёта биллинга. Не со зла: кнопка активна,
снимок красный.

Поэтому роль можно выдать **на один проект**. В «Настройках» рядом с каждым
человеком есть строка прав: выбрать проект, выбрать роль, «+ right».

Правило одно, и оно намеренно простое:

> **Действующая роль в проекте = максимум из глобальной и выданной.**

Право только **поднимает**. Понижающего права нет — иначе администратора можно
было бы лишить доступа к проекту, а чинить это стало бы некому. Отсюда
единственный сценарий изоляции:

1. поставьте людям глобальную роль `viewer`;
2. выдайте `reviewer` на те проекты, за которые они отвечают.

**Обновление ничего не отнимает.** Пока прав не выдано, всё работает ровно как
раньше: глобальный `reviewer` по-прежнему может всё везде. Модель, которая при
накатке образа оставляет команду без человека, способного утвердить эталон,
была бы хуже той дыры, которую она закрывает.

Что считается проектом: ключ подключённого набора (`aeron-api-tests`), а для
собственного набора сервиса — имя его проекта (`service.project` в
`vistest.yaml`, по умолчанию `default`). Собственный набор — тоже проект: иначе
`global` оказался бы единственным местом, где право не спрашивают вовсе, а
именно там у большинства инсталляций и лежат основные эталоны.

Интерфейс считает роль так же, как сервер: кнопка «Принять как эталон» на чужом
проекте не показывается, а вместо неё написано, какой роли и в каком проекте не
хватает. Кнопка, которую сервер заведомо отвергнет, — это не строгий бэкенд, это
неправда на экране.

Выдача и снятие права пишутся в журнал (`rights.granted`, `rights.revoked`) —
это ровно то, о чём спрашивают после происшествия.

| Роут | Что делает |
|---|---|
| `PUT /api/users/{login}/rights/{project}` | `{role}` — выдать право |
| `DELETE /api/users/{login}/rights/{project}` | снять |
| `GET /api/users` | люди вместе с их правами и список проектов |

С машины сервиса — то же самое командой (пригодится, когда интерфейс
недоступен, и когда права раздаются скриптом при развёртывании):

```bash
vistest user grant vic aeron-api-tests reviewer
vistest user rights            # кто, где и что может
vistest user revoke vic aeron-api-tests
```

## 9.1. Decisions: очередь решений

Экран прогона отвечает на вопрос «что сломалось здесь». Человек, открывающий
VisTest утром, задаёт другой: **что от меня требуется**. И это не список из
двадцати трёх картинок.

Разница дорогая, и она та же, что у кластеризации: двадцать снимков покраснели
от одной правки line-height, человек разбирает их по одному, к пятому перестаёт
смотреть, к десятому принимает не глядя. Кластеры внутри прогона лечили это
наполовину — надо было сначала найти нужный прогон и открыть его. Падение,
приехавшее три прогона назад и с тех пор повторяющееся, в списке последнего
прогона неотличимо от свежего, а в списках предыдущих его никто не ищет.

**Decisions** строит очередь по проекту и по причинам:

| Число | Что означает |
|---|---|
| **TO DECIDE** | причин, ждущих ответа, и снимков за ними |
| **BLOCKED** | снимки с вердиктом `error` — картинки нет, сравнивать не с чем |
| **CLEAN** | зелёных из всех снимков набора |
| **RUN** | последний прогон: длительность и когда |

Три решения, каждое из которых можно было принять неправильно.

**Снимок считается один раз — по последнему сравнению.** Одно и то же падение,
повторившееся в пяти прогонах, это один вопрос, а не пять. Счётчик, который в
пять раз завышает, перестают читать в тот же день.

**Каждый снимок попадает ровно в одну причину.** Регион может подойти двум
кластерам сразу; отдать снимок обоим — значит получить сумму причин больше числа
красных и человека, который ответил на всё, а счётчик не обнулился.

**Причин без объяснения не бывает.** Снимок, для которого общей причины не
нашлось, не исчезает: он становится причиной из одного снимка. Тихо потерять
неразобранное падение — ровно та поломка, ради которой очередь и написана.

Ответ на причину — **один запрос** на все её сравнения
(`POST /api/comparisons/bulk`). Цикл из одиннадцати запросов был бы не
«медленнее», а хуже по смыслу: каждый может упасть сам по себе и оставить
причину решённой наполовину, а защита от чужого решения в такой цикл не
помещается.

`Blocked` в очередь решений не идёт: решать там нечего. Но и молчать нельзя —
«ноль красных» при двух неснятых страницах это не хорошая новость, а отсутствие
проверки. Кнопка «Retry» перезапускает снимок **тем же способом, которым он
снимался**: через его тест, если он снят тестом.

Очередь строится для одного набора: причина объединяет снимки одного проекта, и
общее решение для двух чужих друг другу наборов бессмысленно. При «всех
проектах» экран предлагает выбрать, чью очередь открыть; если проект один,
ничего не спрашивает.

| Роут | Что делает |
|---|---|
| `GET /api/decisions?project=<name>` | причины, blocked и счётчики одним ответом |

### Фоновые задачи и перезапуск

Снять эталон по URL или прогнать набор — это десятки секунд, поэтому такие
действия идут задачей в фоне: интерфейс опрашивает её статус и показывает лог по
мере поступления.

Задача переживает перезапуск сервиса — точнее, переживает **её запись**. Сама
задача продолжиться не может: внутри неё крутится чужой pytest или браузер, и
после смерти процесса продолжать нечего. Но пропадать бесследно она не должна, а
раньше именно это и происходило: человек нажимал «Прогнать», уходил, в это время
выкатывали обновление образа — и задача исчезала. Не «упала», не «прервана», а
переставала существовать: опрос получал 404, а интерфейс писал «connection to the
task lost», то есть винил сеть в том, к чему сеть отношения не имеет.

Теперь такая задача остаётся в списке, получает статус «прервана перезапуском» и
сохраняет хвост лога — причина написана именно там. «Всё ещё running» после
перезапуска было бы враньём: за этой строкой не стоит ни одного живого потока.

Живая задача при этом не пострадает: процесс, который её ведёт, обновляет
отметку времени, и прерванными считаются только те, чья отметка протухла
(`VISTEST_JOB_STALE_S`, по умолчанию 60 секунд). Иначе второй воркер, стартовав,
хоронил бы работающие задачи первого. Проверять по PID нельзя: на Windows
`os.kill(pid, 0)` не спрашивает процесс, жив ли он, а завершает его.

### Уборка истории по расписанию

Дифф на полную страницу — несколько мегабайт PNG. Без уборки `.vistest` съедает
десятки гигабайт за пару месяцев, список из тысяч прогонов начинает тормозить, а
кончается всё «на диске нет места» посреди прогона. Кнопка «почистить старое»
была всегда, но нажимать её надо помнить — то есть не нажимают.

Настраивается в «Настройках» → «Automatic cleanup»: срок, «сколько последних
беречь всегда» и предел по диску. **Выключено по умолчанию** — это единственное
фоновое действие, которое удаляет данные, а инсталляция на ноутбуке одного
инженера проблемы с диском не имеет.

Три правила, о которых стоит знать до включения:

* **Неразобранное падение не удаляется никогда** — ни сроком, ни квотой, ни
  кнопкой. Это единственное правило без переключателя. Такое падение — вопрос, на
  который никто не ответил, и удалить его значит сделать так, что уже и не
  ответит. Разобранное — другое дело: решение принято, и его текст остаётся в
  истории снимка.
* **«Беречь последние N» считается по каждому проекту отдельно.** Общий список
  означал бы, что активный проект вытесняет из-под защиты редкий: у того прогонов
  мало, они старые, и «последние пятьдесят» до них просто не доходят.
* **Эталоны не трогаются вообще.** Прогон — это история проверок, а не источник
  правды.

Предел по диску отвечает на другой вопрос, чем срок: срок говорит «это уже не
нужно», предел — «место кончается». Поэтому при переполнении удаляются самые
старые независимо от возраста, и ровно столько, чтобы влезть, — «раз уж чистим,
почистим с запасом» это чужие данные, удалённые без причины.

Кнопка **«Show what would go»** показывает список, ничего не удаляя, и называет
причину в обоих случаях. «Ничего не уйдёт» без объяснения читается как «политика
не работает», и следующим действием человек выкручивает срок в единицу.

| Роут | Что делает |
|---|---|
| `GET/PUT /api/settings/retention` | срок, «беречь последние», предел по диску |
| `POST /api/settings/retention/preview` | что ушло бы прямо сейчас, не удаляя |
| `POST /api/runs/cleanup` | разовая уборка — по той же политике |

Часы тикают раз в сутки (`VISTEST_RETENTION_TICK_S`; `0` выключает).

### Лог запросов и `X-Request-Id`

Диагностика держалась целиком на логе задачи, а про сам сервис не было известно
ничего: ни какой запрос пришёл, ни сколько он шёл, ни чем кончился. Разговор при
отказе выглядел так: «у меня не сохранилось» — «а когда?» — «ну, недавно».

Теперь на каждый запрос пишется одна строка (метод, путь, код, длительность,
кто спрашивал) и каждый ответ несёт `X-Request-Id`. Его же несёт текст любой
пятисотки, так что человек может процитировать строчку из интерфейса вместо
пересказа. Если идентификатор пришёл снаружи — от прокси или чужого конвейера —
берётся он: своя нумерация поверх чужой рвёт трассировку ровно там, где она и
нужна.

`VISTEST_LOG_FORMAT=json` — строки в JSON для сборщика; по умолчанию текст,
потому что сервис чаще смотрят глазами в терминале.

Чего в логе нет намеренно:

* **тела запроса** — в нём проезжают пароли из формы входа и значения
  `secrets.env`; лог, в который однажды попал чужой пароль, это утечка, живущая
  столько же, сколько живут ротации;
* **строки запроса** — там же токен метрик (`/metrics?token=…`);
* **опроса статуса и статики** — он ходит раз в 700 мс, и одна открытая вкладка
  даёт полторы тысячи строк в час, в которых тонет всё остальное.

### Отправка прогонов

Раннер по умолчанию работает офлайн — пишет только файлы. Чтобы результаты
попадали в UI:

```bash
python run.py test --api http://127.0.0.1:8420
# или
set VISTEST_API_URL=http://127.0.0.1:8420      # Windows
export VISTEST_API_URL=http://127.0.0.1:8420   # Linux/macOS
```

Или в `vistest.yaml`:

```yaml
service:
  api_url: http://127.0.0.1:8420
  project: my-shop
  fail_open: true    # недоступный сервис не роняет тесты
```

Если сервис лежал во время прогона, результаты остаются в `.vistest/runs/` с
пометкой `.pending`. Догрузить позже:

```bash
python run.py push
```

### Что есть в UI

Навигация сгруппирована по вопросу, а не по объекту, и порядок групп — это
порядок частоты обращения:

| Группа | Экраны | На какой вопрос отвечает |
|---|---|---|
| REVIEW | Decisions, Runs | что от меня требуется; что было |
| LIBRARY | Baselines, Tests | что у нас вообще есть |
| HEALTH | Trust, Environment | можно ли этому верить |
| SETUP | Projects, Settings | как это настроено |

**Decisions** — главный экран и точка входа. Он отвечает не на «что красное», а
на «на что ответить»: подробности в разделе
[9.1](#91-decisions-очередь-решений).

**Прогоны** — таблица истории: когда, чем кончилось, на какой ветке. Прогон
открывается отдельной страницей во всю ширину — со сводкой, причинами и
таблицей снимков. Раньше список и карточка делили экран пополам, и половина
ширины уходила на список, в котором уже не было нужды.

**Эталоны** — сетка снимков с превью. Набор и платформа переключаются строкой
над сеткой, там же фильтр по имени. Здесь же заводятся новые: вбиваете адрес,
имя, размер окна и при необходимости селектор — эталон снимается
headless-браузером на сервере.

У каждого снимка есть паспорт: адрес, размер окна, селектор, пауза. Кнопка
«Адрес» привязывает его к уже существующему эталону — в том числе к снятому
через `record` или созданному кодом. Как только адрес задан, снимок становится
запускаемым:

- **Проверить** — снять страницу заново и сравнить с эталоном
- **Переснять** — принять текущее состояние как новый эталон
- **Проверить все с адресом** — прогон всего набора одной кнопкой

Это полноценный способ вести визуальные тесты вообще без кода: адреса привязаны
к снимкам, движок сравнения тот же самый, результаты уходят в историю прогонов.
Кнопка «Запустить pytest» рядом — для набора, написанного кодом.

Ход выполнения виден в логе под кнопками: этап за этапом, с таймингом и
возможностью отменить.

**Разбор сравнения (триаж)** — слева картинки и регионы, справа колонка
решения. Наверху полоса очереди: точками видно, сколько уже разобрано и сколько
осталось, — число «4 / 23» отвечает на «где я», а точки на «сколько ещё», и это
разные вопросы. Ответ ведёт сразу к следующему снимку, а не обратно в список.

Клавиши названы прямо на кнопках: **A** — принять как эталон, **B** — это баг,
**D** — отложить, **M** — заглушить область, **J**/**K** — вперёд и назад по
очереди, **1**–**6** — режимы просмотра. Горячая клавиша, о которой знает только
автор, не существует.

Если снимок пришёл из очереди и у его причины есть другие снимки, в правой
колонке появляется «Accept all N» — ответ за всю группу одним запросом. Он стоит
**ниже** одиночного решения намеренно: сначала человек смотрит на конкретный
снимок, и только потом ему предлагают распространить ответ.

**Просмотр сравнения** — шесть режимов:

- *Слайдер* — шторка между было/стало, поверх рамки регионов
- *Blink* — мигание
- *Onion skin* — красное было, голубое стало
- *Разметка* — рамки с классами
- *Тепловая карта* — ΔE00
- *Рядом* — триптих

Регионы — карточками под картинкой, у каждого свой крупный план: эталон,
текущее состояние и карта ΔE00. Рядом кнопка «Ignore area» — заглушить ровно эту
область, названную явно.

**Trust** (бывшие «Метрики») — доля ложных падений, гистограмма severity против
порога, самые шумные и самые медленные снимки, мёртвый груз без прогонов за 30
дней. Число ложных падений продублировано в навигации: оно отвечает, стоит ли
верить всему остальному.

**Environment** (бывшая «Диагностика») — сколько падений даёт неизменившаяся
страница. Это число тоже стоит в сайдбаре внизу, всегда: смотреть на него надо
не тогда, когда за ним пришли.

**Настройки** — переменные среды для сценариев за логином.

Без них «завести визуальные тесты без кода» перестаёт быть правдой на первой же
странице с формой входа: шаги ссылаются на `${VISTEST_USER}` и
`${VISTEST_PASSWORD}`, а взять значения раньше было неоткуда, кроме как править
`.vistest/secrets.env` руками.

Вкладка делает три вещи:

- показывает и правит переменные — построчно или файлом целиком;
- сама находит, **чего не хватает**: сканирует `vistest.yaml` и паспорта
  эталонов, собирает все упоминания `${...}` и подставляет недостающие имена
  пустыми строками. Прогон не падает с «неизвестная переменная» — вы видите
  это заранее;
- применяет значения к работающему сервису сразу, без перезапуска.

**Про безопасность честно.** Файл содержит пароли к стенду, и здесь он
редактируется как обычный текст: значения ходят по HTTP в открытом виде.
Это допустимо ровно в том режиме, для которого VisTest и сделан — сервис на
loopback у инженера или внутри контура. Поэтому:

| Режим | Поведение |
|---|---|
| по умолчанию | эндпоинты отвечают только на запросы с localhost |
| `VISTEST_SECRETS_UI=all` | доступ откуда угодно — осознанное решение |
| `VISTEST_SECRETS_UI=off` | редактор выключен совсем |

Сам файл пишется с правами 0600 и лежит в `.gitignore`. Если инсталляция
выставлена наружу (`--host 0.0.0.0`), ставьте `off` и правьте файл на машине.

### Уборка: удаление эталонов и прогонов

Прогоны копятся быстро: каждый полностраничный дифф — несколько мегабайт PNG.
Без ретенции каталог `.vistest` за пару месяцев съедает десятки гигабайт, а UI
начинает тормозить на списке из тысяч записей.

**В UI.** На вкладке «Прогоны»: крестик на карточке в списке и кнопка «✕ Удалить
прогон» в шапке. Кнопка «🧹 Очистить старые» удаляет всё старше N дней —
перед этим показывает, сколько сейчас занято. Последние 20 прогонов сохраняются
всегда: даже старые они нужны как точка отсчёта, если сегодня всё сломалось.

На вкладке «Эталоны»: крестик на карточке, режим «☑ Выбрать» для пакетного
удаления и «🗑 Удалить платформу» — снести весь набор, например после смены
браузера или дизайн-системы.

При удалении эталона отдельно спрашивается, стирать ли историю проверок по нему.
Разделено намеренно: снимок могли удалить временно, а метрики за месяцы терять
не всегда нужно. Если историю оставить — удалённые снимки продолжат числиться
на дашборде; если стереть — исчезнут и оттуда.

**Из командной строки:**

```bash
python run.py rm home.png cart.png       # конкретные эталоны
python run.py rm --all --platform win-chromium-1x
python run.py rm --all -y                # без подтверждения (для скриптов)

python run.py prune --days 30            # прогоны старше 30 дней
python run.py prune --days 7 --keep-last 50
python run.py prune --days 30 --runs-only  # только файлы, записи в БД оставить
```

`prune` показывает список и объём до удаления и требует подтверждения, если не
передан `-y`.

**По HTTP:**

```
DELETE /api/runs/{id}                    удалить прогон и его артефакты
POST   /api/runs/cleanup {days, keep_last, only_passed}
DELETE /api/comparisons/{id}
DELETE /api/snapshots/{id}/history        стереть историю, оставив эталон
POST   /api/baselines/delete {platform, names|all, purge_history}
DELETE /api/baselines/{platform}/{name}?purge_history=true
GET    /api/storage                       сколько занято
```

Удаление платформы целиком требует явного `all: true` — пустой список имён как
«удалить всё» слишком легко получить из-за опечатки на клиенте. Все операции с
файлами ограничены каталогом `.vistest`: пути в базе приходят в том числе с
других машин, и снести что-то за его пределами недопустимо.

Что удаление **не** трогает: `prune` и удаление прогона не затрагивают эталоны —
это история проверок, а не источник правды. И наоборот, удаление эталона не
ломает прошлые прогоны: их артефакты остаются на месте.

### Prometheus

```
GET /metrics
```

Отдаёт `vistest_comparisons_total`, `vistest_regions_total{kind}`,
`vistest_snapshot_fail_rate{snapshot}`, `vistest_false_fail_rate`.

Готовый конфиг для скрейпа — `docker/prometheus.yml`, поднимается профилем:

```bash
docker compose -f docker/docker-compose.yml --profile metrics up -d
```

**`false_fail_rate`** — главная метрика здоровья: доля падений, которые человек
посмотрел и заапрувил. Растёт — значит движок шумит, пороги надо править.

## 10. Docker и CI

### Зачем контейнер

Скриншот зависит от версии браузера, набора шрифтов, hinting'а и субпиксельного
сглаживания. Пока эти четыре вещи не зафиксированы, одинаковые эталоны между
машинами невозможны в принципе. Образ раннера фиксирует всё это: прибитая
версия `mcr.microsoft.com/playwright/python`, явный набор шрифтов,
`--font-render-hinting=none --disable-lcd-text --force-color-profile=srgb`.

### Команды

```bash
python run.py docker          # поднять сервис + UI
python run.py docker test     # прогнать тесты в контейнере
python run.py docker down     # остановить

# напрямую
docker compose -f docker/docker-compose.yml up -d api
docker compose -f docker/docker-compose.yml --profile test run --rm runner
```

Эталоны из контейнера складываются в отдельный ключ `docker-chromium-1x` и в
том `vistest-baselines` — они не перемешиваются с локальными.

### Результат для CI: JUnit и код возврата

Код возврата есть только у pytest. Прогон подключённого проекта в режиме
наблюдения (их тесты уже отработали, наш вердикт пересчитан отдельно) и прогон,
запущенный кнопкой в интерфейсе, никакого pytest не имеют — для конвейера их
результат не существовал вовсе.

```bash
python -m vistest.cli gate --junit junit-visual.xml
```

Читает последний прогон в `.vistest/runs` (или указанный `--run`), пишет JUnit
XML и возвращает **0 или 1**. Сервис ему не нужен: `run.json` пишется всегда, в
том числе офлайн.

| Что в прогоне | Что в JUnit | Останавливает конвейер |
|---|---|---|
| `pass` | testcase | нет |
| `fail` | `<failure>` с severity, площадью, SSIM и списком регионов | да |
| `fail`, уже принятый человеком как норма | обычный testcase + `system-out` с автором решения | нет |
| `error` — съёмка или движок упали | `<error>` | да |
| `new_baseline` | `<skipped>` | нет (`--fail-on-new` меняет) |

Про принятые падения отдельно: решение уже принято человеком, и красный CI
после него — просто шум. Пересобрать артефакт после разбора и получить зелёный
— ровно то, чего от такой выгрузки ждут. `--ignore-review` даёт картину на
момент прогона.

Тот же файл доступен из сервиса — `GET /api/runs/{id}/junit.xml` и кнопка
«JUnit for CI» на карточке прогона; решение отдельно — `GET /api/runs/{id}/gate`.
А `junit.xml` кладётся рядом с `run.json` в каталоге каждого прогона сам по
себе, без всяких команд.

### Комментарий в PR/MR

```bash
python -m vistest.cli comment --out visual-comment.md
gh pr comment "$PR" --body-file visual-comment.md      # GitHub
glab mr note "$CI_MERGE_REQUEST_IID" -m "$(cat visual-comment.md)"   # GitLab
```

**VisTest рендерит, CI публикует.** Разделение намеренное. Соблазн был
противоположный — научить сервис ходить в GitHub и GitLab самому. Это значило
бы держать по клиенту на каждую площадку, просить токен с правом писать в ваши
репозитории и хранить этот токен у себя. Взамен — ничего, чего не делает одна
строчка `gh pr comment --body-file`: публиковать умеет CI, и умеет лучше — он
уже аутентифицирован и уже знает номер PR.

Что в комментарии и почему именно так — его читают в ленте, между чужими
сообщениями, и читают быстро:

* **первая строка — ответ**, а не заголовок: «3 of 47 snapshots changed».
  Заголовок «VisTest report» не сообщает ничего, а решение открывать остальное
  по нему уже принято;
* **падения свёрнуты по общей причине**. Двадцать красных снимков от одного
  отступа в шапке — это один вопрос, а не двадцать; показать двадцать строк
  значит заставить человека восстанавливать группировку самому;
* **таблица обрезается** и говорит об этом. Сотню строк никто не пролистает, а
  молчаливая обрезка читается как «это всё»;
* **принятые падения не считаются изменениями** — решение уже принято, спросить
  второй раз значит шуметь;
* **ноль снимков — это не «всё хорошо»**, а «проверки не было». Тесты не сняли
  ничего (сломался селектор, упал браузер), а комментарий зелёный — самый
  неприятный из возможных обманов;
* если включён [эталон на ветку](#52-эталон-на-ветку), комментарий говорит, **в
  чей набор уедет «принять»**. Без этой строки он советует принять изменение и
  молчит о том, что базовый набор останется со старыми картинками.

`VISTEST_PUBLIC_URL` — адрес, под которым сервис видно снаружи. Без него в
комментарии не будет ссылок вовсе, и это правильнее, чем ссылка на `localhost`,
не работающая ни у одного читателя PR.

Тот же текст отдаёт сервис — `GET /api/runs/{id}/comment.md`.

### Отчёт на странице сборки GitHub

JUnit показывают все, но не на первом экране: в GitHub Actions до списка тестов
надо провалиться в шаг. А смотрят на страницу сборки — и видели там ровно
`Process completed with exit code 1`.

`vistest gate` заполняет два штатных места GitHub, если видит его переменные
окружения, — и оба это просто файл и просто stdout, без токенов и без сети:

* `$GITHUB_STEP_SUMMARY` — **та же самая** сводка, что уходит в комментарий PR.
  Именно та же, а не похожая: две почти одинаковые расходятся на третьем
  изменении, и человек начинает сверять их между собой вместо того, чтобы
  смотреть на дифф;
* `::error` — аннотация на каждый блокирующий снимок, в списке проблем сборки.

У GitLab аналога нет — он читает JUnit и показывает его сам, поэтому там ничего
и не печатается.

### GitHub Actions

Готовый workflow — `.github/workflows/visual.yml`. Что делает:

1. Гоняет тесты в **том же образе**, что и локальный docker-режим.
2. Кладёт `.vistest/runs/` в артефакты (14 дней).
3. Считает вердикт (`vistest gate`), пишет JUnit и заполняет страницу сборки.
4. Пишет комментарий в PR — через `vistest comment` и `gh pr comment`.
5. Роняет джобу, если гейт сказал «стоп».

Раньше пункт 4 был двадцатью строками JavaScript прямо в YAML, разбиравшими
`run.json` руками. Логика отображения жила в конфиге пайплайна, ничем не
проверялась и тихо ломалась при любом переименовании поля; теперь это команда,
у которой есть тесты.

Чтобы эталоны были в CI — они должны быть закоммичены (лучше через git-lfs,
`checkout` в workflow уже с `lfs: true`).

### GitLab CI

Готовый набор job'ов — [`.gitlab-ci.example.yml`](../.gitlab-ci.example.yml).
Отдельным файлом-примером, а не готовым `.gitlab-ci.yml`, потому что у проекта
почти наверняка уже есть свой пайплайн, и подменять его целиком неправильно —
скопируйте нужное.

Что там есть:

| Job | Что делает |
|---|---|
| `visual:test` | прогон в том же образе, что и локальный docker-режим; артефакты и оффлайн-отчёт |
| `visual:project` | прогон подключённого извне набора тестов |
| `visual:update-baselines` | обновление эталонов — **только вручную**, с коммитом в ветку |
| `visual:doctor` | измерение шума стенда по расписанию |

Три вещи, на которых обычно спотыкаются:

**Образ должен совпадать.** Эталоны и прогон обязаны рождаться в одном и том же
образе — иначе рендер текста разойдётся, и совпадения не будет никогда. Для
полной воспроизводимости пиньте образ по digest, а не по тегу: тег
`v1.47.0-jammy` может быть пересобран.

**Тесты гоняются последовательно.** Параллельный запуск даёт конкуренцию за CPU,
отчего анимации и таймауты ведут себя иначе, и снимки начинают дрожать. Экономия
времени того не стоит.

**Обновление эталонов — только руками.** `--vistest-update` в регулярном
пайплайне означает, что тесты больше ничего не проверяют: любая поломка молча
становится новой нормой. В примере этот job ручной и коммитит результат в ветку,
где его увидят на ревью.

Эталоны должны быть закоммичены — лучше через git-lfs, в примере есть `git lfs pull`.

## 11. AI-слой

Три независимых компонента, каждый отключается отдельно. Без них движок
полностью работоспособен.

### DOM-attribution — включён по умолчанию

Не требует моделей и сети: это пересечение геометрии региона с bbox элементов
из DOM-снепшота. Даёт в отчёте имя элемента вместо координат:

```
[removed] button[data-testid="checkout-submit"] "Оформить заказ"
```

Работает лучше, если у элементов есть `data-testid`.

### Перцептивная модель

Отсеивает изменения, заметные математически, но не человеку: пережатие JPEG,
другой dithering градиента, чуть другое сглаживание иконки.

```bash
pip install torch torchvision                     # только для экспорта
python scripts/export_perceptual_model.py --arch mobilenetv3
```

```yaml
ai:
  perceptual_enabled: true
  perceptual_model_path: models/perceptual.onnx
  perceptual_tolerance: 0.06     # cos-distance ниже → регион считается шумом
```

Или разово: `python run.py test --preset balanced` с `VISTEST_PERCEPTUAL=1`.

Модель ~10–30 МБ, работает на CPU, ~5 мс на регион. Если `onnxruntime` не стоит
или файла модели нет — слой молча выключается.

### Vision-LLM каптионер

Описывает регресс словами для PR-комментария. Ходит в сеть и стоит денег,
поэтому вызывается только для регионов выше порога severity и только при явном
включении.

```bash
pip install anthropic
export ANTHROPIC_API_KEY=sk-...
```

```yaml
ai:
  captioner_enabled: true
  captioner_min_severity: 40.0
  captioner_max_regions: 5
```

Результат попадает в поле `caption` региона, в UI и в комментарий к PR.

## 13. Траблшутинг

**`Python 3.10+ не найден`** — установите Python и при установке отметьте
«Add to PATH». Проверка: `python --version`.

**PowerShell: «выполнение сценариев отключено»** —
`powershell -ExecutionPolicy Bypass -File .\run.ps1` или один раз
`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

**`ModuleNotFoundError: playwright`** — `python run.py setup`. Проверить:
`python run.py doctor`.

**Браузер не стартует на Linux** — не хватает системных библиотек:
`playwright install-deps chromium` (нужен sudo) или используйте docker-режим.

**Chromium падает в контейнере** — мало `/dev/shm`. В compose уже стоит
`shm_size: 1gb` и `ipc: host`; при ручном запуске добавьте
`--shm-size=1gb --ipc=host`.

**Тесты падают после смены машины/ОС** — это ожидаемо: эталоны разделены по
платформам, для новой платформы их просто нет, они создадутся заново.
Единый набор для всех даёт только docker-режим.

**Всё падает после обновления браузера** — изменился рендер. Проверьте несколько
диффов глазами, затем `python run.py update`. В Docker такого не происходит,
пока версия образа прибита.

**Тест падает, но на картинке ничего не видно** — смотрите `heatmap.png` и
`regions/*.png` с увеличением, или `blink.gif`. Если различие реально
неразличимо — включите перцептивную модель или поднимите `delta_e_threshold`.

**Слишком много ложных падений** — по порядку:
1. `python run.py doctor` — та ли платформа, тот ли браузер;
2. вкладка «Метрики» → список нестабильных снимков;
3. увеличьте `capture.stability_shots` до 5;
4. режьте страницу на компоненты через `clip_selector`;
5. только потом трогайте пороги.

**Тест ничего не находит, хотя изменение есть** — проверьте, не попало ли оно
под маску: `stability.png` рядом с эталоном показывает замаскированную область
белым. Также посмотрите `suppressed` в `result.json` — там причины фильтрации.

**UI пустой** — прогоны не отправлялись в сервис. Запустите с
`--api http://127.0.0.1:8420` или выполните `python run.py push`.

**`sqlite3.OperationalError: database is locked`** — параллельные прогоны в один
SQLite. Для нагруженного CI переключитесь на Postgres или разнесите проекты по
разным `VISTEST_ROOT`.

**Панель записи не появилась** — страница могла запретить внедрение скриптов
(строгий CSP) либо у вас `about:blank`. Перейдите на нужный адрес: панель
переустанавливается на каждой загрузке. При жёстком CSP снимайте через
`vistest snap` или `--cdp`.

**«Снимаю…» висит долго** — смотрите консоль, где запущен `record`: там
печатается текущий этап. Панель тоже показывает его и через 60 секунд без
ответа сообщает об ошибке. Типичные причины на публичных сайтах:

- *бесконечная лента.* После прогрева lazy-load страница вырастает до десятков
  тысяч пикселей, а Chromium не снимает полотна выше ~16000px. VisTest это
  ловит и снимает только первый экран с пометкой в логе. Правильное решение —
  снимать компоненты: кнопка «Выбрать элемент» вместо «Снять страницу», либо
  `--no-scroll`, чтобы не прогревать ленту вовсе.
- *тяжёлая страница.* Три полностраничных кадра большого сайта — это десятки
  секунд. Уменьшите: `--shots 1`.
- *медленная сеть.* `networkidle` на сайтах с рекламой не наступает никогда;
  VisTest ждёт его не дольше 2.5 с и идёт дальше.

Быстрый вариант для тяжёлых сайтов:

```bash
python run.py record https://example.com --shots 1 --no-scroll
```

**Дифф на дате или времени** — самая частая ложная тревога после
анти-алиасинга. Выглядит как поломка вёрстки: в отчёте регион с текстом
«Пятница, 7 августа» против «1 января».

Причина: страница показывает дату, а эталон и прогон видят разное время.
VisTest ставит странице фиксированную точку отсчёта (`capture.frozen_time`,
по умолчанию 1 января 2024) — тогда дата на снимке одна и та же всегда. Часы
при этом **идут** от этой точки, поэтому анимации, дебаунсы и опросы по таймеру
работают нормально: стоящие часы ломают живые приложения.

Если дифф на дате всё-таки появился:

1. Эталон снят раньше, чем детерминизм заработал (например, записан с
   `--no-freeze-time`). Пересоздайте его — кнопка «Переснять» в UI или
   `python run.py update`.
2. Приложение берёт дату с сервера, а не из браузера. Тогда подмена `Date` не
   поможет: маскируйте блок — `data-vistest="ignore"` в вёрстке, селектор в
   `capture.mask_selectors` или игнор-зона в UI.
3. Приложение сломалось от даты 2024 года (протухший токен, «акция
   завершена»). Поставьте свою точку отсчёта в `capture.frozen_time` или
   отключите: `--no-freeze-time` при записи и `capture.determinism: false` в
   конфиге — но тогда дату придётся маскировать.

Отчёт подсказывает это сам: если в изменившемся регионе текст похож на дату,
в заметках появится соответствующий совет.

**Дата отличается между вашей машиной и CI** — не совпадают таймзона и локаль.
Они фиксируются в `capture.timezone` и `capture.locale` (по умолчанию
`Europe/Moscow` и `ru-RU`). Без этого одна и та же страница рендерит разную
дату и разный формат чисел ещё до всякого сравнения.

**`record --cdp` не подключается** — Chrome должен быть запущен с
`--remote-debugging-port=9222` **и** отдельным `--user-data-dir`. Уже
работающий обычный Chrome отладочный порт не откроет.

**Сгенерированный тест падает на первом же прогоне** — типичная причина в том,
что во время записи вы были залогинены, а тест открывает страницу с нуля.
Добавьте в тест шаги авторизации (или фикстуру со стораджем сессии) перед
`page.goto`.

**`POST /api/check` возвращает 400 «неизвестные опции»** — в `options`
разрешён ограниченный список порогов. Полный перечень — в
[`clients/README.md`](../clients/README.md).

**Снимки из JS-клиента расходятся с питоновскими** — проверьте три вещи:
инжектится ли `stabilize.js` (лучше через `installOnContext`, то есть до
загрузки страницы), совпадает ли `deviceScaleFactor`, и одна ли платформа.
Эталоны из Chrome на Windows и из Linux-контейнера несравнимы.
