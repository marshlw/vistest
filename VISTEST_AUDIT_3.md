# VisTest — ревью перед продом (аудит 3)

Дата: 2026-09-05. Объём: ~62k строк (Python 40k, фронт 12k, тесты 20k).
Метод: чтение кода, а не запуск (venv в репозитории — виндовый, тесты не гонялись).
Каждая находка ниже проверена по исходнику; ссылки даны как `файл:строка`.

## Общая оценка

Проект существенно выше среднего для инструмента такого класса. Что сделано хорошо
и не требует правок:

- **Движок сравнения** (`vistest/core/*`) — грамотный: ΔE00 в float32 с чанкованием
  по строкам, консенсус цвет×структура вместо OR, phaseCorrelate с окном Ханна и
  BORDER_REPLICATE, отдельная логика «размазанное расхождение без регионов —
  не падение». Это редко делают правильно.
- **Хранилище эталонов** (`storage/fs.py`) — dir-lock, атомарная запись через
  `os.replace`, история версий с паспортами, откат.
- **Транзакции** (`api/db.py::connect`) — счётчик вложенности, коммитит только
  внешний уровень. Ровно та ошибка, на которой обычно и получают полупринятые прогоны.
- **Приём прогонов** — `upload_artifact` стримит с жёстким потолком и не верит
  `Content-Length`; ingest требует токен проекта, а не общую переменную.
- **Гонки** — `claim_setup` и `claim_invite` сделаны как compare-and-swap, а не
  «проверил → записал». Дайджест защищён от нескольких реплик тем же приёмом.
- **Комментарии** объясняют «почему», а не «что». Это дорогого стоит.

Ниже — то, что мешает называть систему прод-готовой. Порядок: сначала блокеры,
потом баги корректности, потом нефункциональное, потом функциональные пробелы.

## 1. Блокеры (чинить до любого внешнего доступа)

### S1 — КРИТИЧНО. Вся «локальная» граница безопасности обходится HTTP-заголовком

`docker/Dockerfile.api` запускает сервис с `--forwarded-allow-ips *`.
В uvicorn это `always_trust=True`, и тогда
`proxy_headers.py::get_trusted_client_address` берёт **первый** элемент
`X-Forwarded-For` — то есть тот, который целиком контролирует клиент
(проверено в `.venv/Lib/site-packages/uvicorn/middleware/proxy_headers.py:176-177`).
Caddy дописывает реальный IP **в конец**, поэтому даже за правильно настроенным
прокси первый элемент остаётся клиентским. `request.client.host` управляется
атакующим.

На `request.client.host` держится:

| Место | Что защищает |
|---|---|
| `api/main.py:145-151` `_is_loopback` → `_open_install` | доступ к инсталляции, у которой ещё нет администратора |
| `api/projects.py:105` `_guard` (`VISTEST_PROJECTS_UI=local` по умолчанию) | подключение проекта = **запуск произвольного процесса** |
| `api/baselines.py:85` (`VISTEST_TESTS_UI=local`) | правка и запуск тестов на машине сервиса |
| `api/settings.py:76` (`VISTEST_SECRETS_UI=local`) | чтение и запись `secrets.env` |
| `api/record.py:68` (`VISTEST_RECORD_UI=local`) | запуск браузера на машине сервиса |
| `api/auth.py:791` | троттлинг входа по адресу |

Худший сценарий, целиком из наблюдаемого поведения: свежий контейнер поднят,
администратора ещё нет. Запрос с `X-Forwarded-For: 127.0.0.1` проходит
`_open_install`, а `current_user` (`api/auth.py:604`) при отсутствии активных
пользователей выдаёт роль `admin` кому угодно. Дальше `POST /api/projects` с
`runner: "command"` и произвольным `command` — и это **удалённое исполнение кода
без аутентификации**. На инсталляции с пользователями остаётся вход в
`secrets.env` и обход IP-троттлинга.

Что делать:

1. `--forwarded-allow-ips` — конкретный адрес прокси, никогда `*`. В Dockerfile
   значение брать из `VISTEST_TRUSTED_PROXY` (по умолчанию пусто = не доверять).
2. Развести два понятия: `request.client.host` (кто по мнению прокси) и **сырой
   peer** соединения. Локальные гварды и троттлинг обязаны смотреть на сырой peer.
   Практически: свой ASGI-middleware, который до ProxyHeaders кладёт
   `scope["client"]` в `scope["state"]["peer"]`, и `_is_loopback`/`_guard`/
   `login` читают его.
3. Отдельно: `_open_install` не должен опираться только на loopback. Ввести
   обязательный `VISTEST_SETUP_TOKEN` для любой инсталляции, слушающей не на
   `127.0.0.1`, и отказываться стартовать с `--host 0.0.0.0` без него.

### S2 — ВЫСОКО. Открытая регистрация — усилитель нагрузки и мусор в очереди

`api/auth.py` `register` вызывает `create_user` → `hash_password`
(PBKDF2, 480 000 раундов, `auth.py:73`) **до** каких-либо ограничений.
Регистрация включена по умолчанию (`open_registration`, `auth.py:222`),
троттлинга на ней нет — он стоит только на `login`. Двадцать параллельных
POST'ов без единого пароля съедают весь CPU сервиса; параллельно база
наполняется заявками, которые некому разгребать.

Чинить: тот же счётчик по журналу, что и у входа, на `register`, `setup`,
`accept-invite`; потолок на число `pending` (например 50, дальше 429);
`open_registration` по умолчанию **выключить** для инсталляций, слушающих не
loopback.

### S3 — ВЫСОКО. `POST /api/check` читает файлы в память без лимита

`api/check.py:145-146`:

```python
rgb = _decode(await image.read())
extra = [_decode(await f.read()) for f in frames if f is not None]
```

Ни лимита на размер файла, ни на число `frames`, ни на пиксели после декода
(`_decode` идёт в PIL/`Image.open` без `MAX_IMAGE_PIXELS`). Это публичная точка
входа для чужих клиентов — ровно та, которую документация зовёт «вход для тестов
на любом языке». Один запрос с десятком файлов кладёт процесс.
В `upload_artifact` (`main.py:466-505`) всё сделано правильно — здесь надо так же:
стриминг во временный файл, `MAX_ARTIFACT_BYTES`, `MAX_FRAMES`, проверка
`Image.open(...).size` до `convert("RGB")`.

### S4 — ВЫСОКО. Загрузка проекта: весь архив в память + zip-бомба

`api/projects.py:196-217`: `data = await file.read()` стоит **до** проверки
`len(data) > MAX_UPLOAD` — то есть 200 МБ лимит не защищает ни от чего, память
уже занята (и не 200 МБ, а сколько прислали). Zip-slip проверен корректно, а вот
суммарный распакованный размер — нет: `zf.extractall(dest)` без учёта
`sum(m.file_size)` и числа записей заполняет том данных.

### S5 — СРЕДНЕ. `_resolve()` выпускает за пределы каталога данных

`api/main.py` (конец файла):

```python
def _resolve(uri):
    if uri.startswith("/files/"): return (ARTIFACTS / uri[len("/files/"):]).resolve()
    if uri.startswith("/local/"): return (ROOT / uri[len("/local/"):]).resolve()
    p = Path(uri); return p if p.exists() else None
```

Ни `is_relative_to`, ни отказа на абсолютный путь. Значение приходит из
`artifacts.actual` в теле `POST /api/runs`, то есть из внешнего CI, и попадает
в `_approve_one` → `read_png(src)` → `store.save(...)`. Итог: произвольный файл
с диска сервера можно превратить в эталон и потом скачать через `/files`.
Требуется владение ingest-токеном, но это ровно та роль, которая по замыслу
файлов сервера видеть не должна.

### S6 — СРЕДНЕ. Схема API открыта анонимно

`PUBLIC_PREFIXES` в `api/main.py:139` включает `/docs`, `/redoc`,
`/openapi.json`. Полная карта роутов до входа. В проде: `FastAPI(docs_url=None,
redoc_url=None, openapi_url=None)` если не задан `VISTEST_DOCS=on`.

### S7 — СРЕДНЕ. Блокировка входа блокирует жертву, а не атакующего

`auth.py:398-408`: 8 неудач по логину за 15 минут — и владелец учётки не может
войти. Достаточно знать чужой логин. Лучше: экспоненциальная задержка ответа
вместо отказа, блокировка по паре (логин + сырой peer), а по одному логину —
порог заметно выше и с уведомлением в журнал.

### S8 — СРЕДНЕ. Нет заголовков безопасности на интерфейсе

`/ui/` отдаётся без `Content-Security-Policy`, `X-Frame-Options`
(`frame-ancestors`), `Referrer-Policy`, `X-Content-Type-Options`. Кнопка
«Принять как эталон» — необратимое действие, которое отлично кликджекается.
`/files` заголовки имеет, а сам UI — нет.

### S9 — СРЕДНЕ. CSRF держится только на `SameSite=Lax`

Своего токена нет. Пока CORS без credentials — приемлемо; как только
администратор задаст `VISTEST_CORS_ORIGINS` (`main.py:246`), любой скрипт на
разрешённом origin получает полные права сессии. Дешёвая страховка: требовать
на всех мутациях заголовок `X-VisTest-UI: 1` (простые формы его не отправят) или
double-submit cookie.

### S10 — НИЗКО, но для SaaS-варианта обязательно

- SSRF-hardening вебхука (`api/notify.py:189`): схема проверяется, приватные
  диапазоны и `169.254.169.254` — нет.
- `secrets.env` лежит открытым текстом (0600), доступен через UI и уезжает
  в бэкап тома. Как минимум: не возвращать значения через API (только маски
  и признак «задано»), писать в журнал факт чтения.
- Регулярки из формы (`api/projects.py::_clean_naming`) компилируются и
  применяются к именам файлов — ReDoS. Ограничить длину и число квантификаторов.

## 2. Ошибки корректности

### B1 — Артефакты матричного прогона перетирают друг друга

`api/main.py:487` — `dest_dir = ARTIFACTS / str(run_id) / _safe(snapshot)`.
Платформы в пути нет. В прогоне по матрице `chromium@1440` и `firefox@390` —
это один и тот же снимок по имени, и их `actual.png`/`heatmap.png` пишутся
в один каталог: последний выигрывает.

Там же `main.py:513-516` привязка URI:

```sql
SELECT c.id, c.artifacts FROM comparison c JOIN snapshot s ON s.id=c.snapshot_id
 WHERE c.run_id=? AND s.name=?
```

Шесть сравнений одного имени в прогоне, `db.one` берёт произвольное.
Ирония в том, что в `ingest_run` (`db.py`) платформа сравнения уже учтена
правильно — и комментарий там объясняет ровно эту проблему. Здесь её забыли.

Чинить: `platform` в путь артефакта и в `WHERE`; форма `POST` должна принимать
платформу (с обратной совместимостью — при отсутствии старое поведение).

### B2 — `add_ignore_box` рушит паспорт эталона

`storage/fs.py:440-452`: read-modify-write `meta.json` **без** `_dir_lock` и
**без** атомарной записи, при том что `save()` рядом делает и то, и другое,
и в докстринге объяснено почему.

Два «Ignore area» подряд теряют одну зону. Хуже: обрыв на `write_text` оставляет
битый JSON, а дальше `_baseline_state` (`main.py:1128`) молча вернёт
`version: 0` — то есть защита от конкурентного апрува выключится, — и следующий
`save()` не прочитает `prev_meta`, начнёт версии с 1 и потеряет `ignore_boxes`.

Правка на пять строк: обернуть в `with _dir_lock(d):` и писать через
`_write_atomic_text`.

### B3 — Фоновые задачи и тикеры живут в процессе, а разворачивают несколько

`api/main.py:80-98` создаёт `_jobs_runner.bind`, `_notify.ensure_ticker`,
`_retention.ensure_ticker` на импорте модуля. При `uvicorn --workers N` или
нескольких репликах за общим томом:

- `retention` (`api/retention.py:305`) удаляет данные из каждого воркера
  независимо — защиты вида compare-and-swap, как в `notify::_claim`, здесь нет;
- `lock_key` в `api/jobs.py:443` — внутрипроцессный лок. Два прогона одного
  проекта пойдут параллельно и будут писать в одни эталоны;
- `MAX_PARALLEL = 3` тоже на процесс, то есть фактический потолок × N.

Либо advisory-lock в БД для тикеров и очереди (та же техника, что уже
используется в `_claim`), либо явный отказ стартовать при `workers > 1` с
внятным текстом. Сейчас нет ни того, ни другого, и молчаливая порча эталонов —
худший из возможных исходов.

### B4 — Соединения sqlite не закрываются никогда

`api/db.py::_conn` кеширует соединение в `threading.local` по пути и не
закрывает его. FastAPI гоняет синхронные хендлеры в threadpool; при смене
потоков дескрипторы копятся. Плюс `PRAGMA busy_timeout` не выставлен явно
(есть `timeout=15` в `connect`, это оно и есть, но лучше сказать явно и
добавить `synchronous=NORMAL` для WAL).

### B5 — Миграции без версии схемы

`db.py::MIGRATIONS` прогоняется целиком при каждом старте, ошибки глотаются
только по подстроке `duplicate column`. Нет `PRAGMA user_version`, нет отката,
нет защиты «база новее кода» — старый образ, поднятый на новом томе, тихо
работает с чужой схемой. Для прода нужен номер версии, линейный список и отказ
стартовать при версии выше своей.

### B6 — Таблицы, которые растут вечно

- `audit` не чистится, при этом читается на **каждой** попытке входа
  (`_recent_failures`, 2 запроса) — индексы есть, но объём не ограничен ничем;
- `job` в БД не удаляется (в памяти `MAX_JOBS = 50`, в базе — нет);
- `review_claim` — индекс `ix_claim_expires` есть, `DELETE ... WHERE expires_at <`
  не вызывается нигде;
- `purge_expired` (`auth.py:479`) зовётся только из `login` — на инсталляции,
  где никто не входит неделю, протухшие сессии просто лежат.

Всё это — три строки в `retention.run_once`.

### B7 — Переопределения порогов не валидируются по типу

`api/check.py:101` `_ALLOWED_OVERRIDES` фильтрует **имена**, но не значения.
`{"min_region_px": "abc"}` или `{"fail_severity": -5}` доедут до `DiffConfig` и
дадут 500 или бессмысленный вердикт. Нужна pydantic-модель с диапазонами.

### B8 — Массовое утверждение синхронно и неидемпотентно

`main.py::bulk_decision` — до 500 апрувов в одном HTTP-запросе, каждый под
dir-lock и с записью PNG. Докстринг честно говорит, что атомарности нет; но при
обрыве клиента результат неизвестен вовсе, повтор запроса делает всё заново.
Правильное место для этого — `jobs` с прогрессом и идемпотентным ключом.

### B9 — Порядок «404 против 403» непоследователен

`delete_run` и `upload_artifact` сначала проверяют право (комментарий объясняет
почему), а `delete_comparison` (`main.py:1024`) и `delete_snapshot_history`
(`main.py:1034`) — сначала существование. Второй вариант отвечает на вопрос
«а есть ли у вас сравнение №42» тому, у кого прав на него нет.

### B10 / B11 — Дешёвые запросы, которые обходят диск

- `_dir_size` (`main.py`) — `rglob("*")` по всему каталогу артефактов на каждый
  `GET /api/storage` и на каждый тик retention;
- `frontend_stamp` — `rglob` по каталогу фронта на **каждый** `GET /ui/`.
  Кешировать по mtime каталога или считать один раз при старте.

### B12 — Нет потолка на размер изображения в движке

Полностраничный снимок 1440×20000 — это 28 Мпикс; `srgb_to_lab` даёт
float32 H×W×3 (≈345 МБ), плюс второй такой же, плюс `de_map`, плюс SSIM-карта.
При `MAX_PARALLEL = 3` это гарантированный OOM на машине с 8 ГБ. Нужен явный
предел пикселей с понятной ошибкой и опция «уменьшить перед сравнением».

## 3. Эксплуатация и релиз-инженерия

- **O1. Зависимости не зафиксированы.** Нет lock/constraints; в образе
  `pip install -e ".[service]"` — editable-установка в проде. Сборка
  невоспроизводима, обновление транзитивной зависимости может сломать релиз
  молча. Нужен `constraints.txt` (pip-compile), обычная установка в образ,
  `pip-audit` и скан образа (trivy) в CI.
- **O2. Нет `SECURITY.md`**, хотя `auth.py:32` на него прямо ссылается
  («This is written in SECURITY.md»). Нет `CHANGELOG.md`. Нет модели угроз, а её
  главный тезис — «`admin` = исполнение кода на машине сервиса» — обязан быть
  написан явно: это влияет на то, кому дают роль.
- **O3. CI неполон.** Нет порога покрытия, нет типов (mypy), e2e-набор написан,
  но в CI не гоняется, нет проверки миграций на базе прошлой версии, нет сборки
  и запуска docker-образа.
- **O4. Наблюдаемость односторонняя.** `X-Request-Id` и лог на запрос — хорошо;
  но `/metrics` отдаёт только продуктовые метрики. Нет latency/ошибок самого
  сервиса, нет длины очереди задач, нет размера тома. Логи не структурированы
  (не JSON), без `run_id`/`project` в полях.
- **O5. Нет graceful shutdown.** Все фоновые потоки — daemon; на `SIGTERM`
  задача обрывается без отметки (heartbeat спасает только через `STALE_S`).
  FastAPI `lifespan` не используется вовсе, `db`/`cfg`/тикеры создаются на
  импорте — это же мешает и тестам.
- **O6. Нет бэкапа и восстановления.** Ни команды, ни раздела в README. Для
  инструмента, где эталоны — источник правды, это блокер: `vistest backup`
  (`VACUUM INTO` + архив эталонов + `secrets.env` отдельно) и `vistest restore`
  с проверкой версии схемы.
- **O7. Нет потолка на размер тела запроса** на уровне приложения; в
  `deploy/Caddyfile.example` тоже ничего (`request_body max_size`).
- **O8. Версия 0.1.0 и нет версионирования API.** Клиенты для JS и JVM уже
  прибиты к путям `/api/...`; первое же изменение контракта сломает их без
  предупреждения. Ввести `/api/v1` (со старыми путями как алиасами) и правило
  совместимости.

## 4. Чего не хватает пользователю (функционал)

Отсортировано по тому, насколько быстро об этом спросят на демо.

1. **SSO — OIDC/SAML/LDAP.** Первый вопрос любой команды больше десяти человек.
   Сейчас только локальные пароли. Это же снимает половину рисков раздела 1.
2. **Бэкап/восстановление и перенос между инсталляциями** — экспорт набора
   эталонов и импорт в другой инстанс (см. O6). Сейчас единственный способ
   переезда — копировать том руками.
3. **Экран журнала (audit) в интерфейсе.** Таблица есть, пишется хорошо,
   показать негде. «Кто переписал эталон и когда» — вопрос, ради которого
   журнал и заводили.
4. **Уведомления шире вебхука-дайджеста.** Нет форматов Slack/Teams
   (блоками, а не текстом), нет почты, нет уведомления на конкретное событие
   (падение в ветке `main`), только периодический дайджест.
5. **Пагинация и поиск в больших списках.** `GET /api/runs` ограничен 500,
   эталоны отдаются целиком. На двух тысячах снимков интерфейс начнёт тормозить
   на клиенте.
6. **Подключение проекта требует localhost** (`VISTEST_PROJECTS_UI=local`), то
   есть основной сценарий онбординга нельзя пройти из браузера на сетевой
   инсталляции. Открывать его как есть нельзя (это запуск процесса) — нужен
   безопасный путь: подключение по git-URL с фиксированным раннером в песочнице
   вместо произвольного `command`.
7. **Изоляция команд только на уровне развёртывания** (контейнер на команду).
   Для SaaS понадобится настоящая мультиарендность или честная позиция
   «self-hosted, один инстанс на команду» в маркетинге.
8. **Ревью с телефона.** Экран сравнения не адаптивен; «посмотреть диффы в
   дороге» — регулярный запрос у тех, кто платит.
9. **Смешение языков в коде.** Docstring на английском, комментарии и часть
   сообщений на русском (`api/db.py`, `api/auth.py`, `api/main.py`). Для
   публичного AGPL-репозитория с прицелом на зарубежных покупателей это
   заметно и на due diligence, и для контрибьюторов. Решение нужно принять
   одно и до первых внешних PR.
10. **Слой лицензирования под open core** (упомянут в планах) — сейчас его нет
    вовсе, а вводить его после первых установок дороже.

## 5. Порядок работ

**Спринт 1 — «нельзя выпускать без этого»** (оценка: 3–5 дней)

S1 (сырой peer + `--forwarded-allow-ips`), S3, S4, S5, S6, B2, B3.
Критерий готовности: тест, который шлёт `X-Forwarded-For: 127.0.0.1` и получает
403 на `/api/settings`, `/api/projects`, `/api/record/*`; тест на `/api/check`
с файлом больше лимита; тест на параллельные `add_ignore_box`.

**Спринт 2 — надёжность данных** (3–4 дня)

B1, B5, B6, B4, B7, O6 (бэкап), O5 (lifespan вместо импорта).
Критерий: прогон по матрице сохраняет артефакты всех вариантов; база прошлой
версии открывается на новом коде и наоборот — отказом с текстом.

**Спринт 3 — эксплуатация** (3–4 дня)

O1 (constraints + не-editable образ + pip-audit), O2 (SECURITY.md, CHANGELOG,
модель угроз), O3 (e2e и миграции в CI), O4 (метрики сервиса), S8, S9, S7, S2.

**Спринт 4 — продукт** (по объёму — отдельное планирование)

SSO, экран журнала, экспорт/импорт эталонов, пагинация, безопасный онбординг
проекта, решение по языку кода.

## Что перепроверить перед началом

Тесты в этом ревью не запускались (venv в репозитории собран под Windows).
Первым делом стоит прогнать `pytest tests/ --ignore=tests/e2e` и e2e-набор:
часть находок выше — про пути, которые тесты, возможно, уже покрывают, и тогда
объём правки меньше, чем кажется.
